# Rust版・最初の実機会話チェック

現在は会話・戦闘・環境反応・剣への持ち替え・自動川柳・句の共同編集をつなぐ試験版です。敵が残る間の句相談再開まで接続済みで、長期記憶などはまだ移行中です。既存のMLX APIとVOICEVOXは起動したまま使います。

## 起動

1. 通常Python版のドギドサーバーとマイク入力を、それぞれのターミナルで終了する。
2. Rust移植用チェックアウト内の`dogido-rust/start_dialogue.command`を開く。`server_listening`が出るまで待つ。
3. ブラウザーで`http://127.0.0.1:5056/rust-chat`を開く。
4. まず「ゲームなしで会話を試す」を押し、テキストで「こんにちは」と送る。返答本文と「再生完了」が表示され、声が聞こえることを確認する。
5. マイクで試す場合は`dogido-rust/start_voice.command`を開き、待機中になってから話す。

Rust会話試験の発話区切りは無音800msです。起動時に`発話区切り: 無音 800ms`を確認します。通常Python版の共有設定ファイルは変更しません。

起動前の設定・ファイル確認だけなら、各起動ファイルに`--check`を付けます。インストール、モデル起動、録音は行いません。API認証を設定している場合は、画面上部の認証欄へ同じトークンを入力してください。画面はトークンを保存しません。

## Minecraftの観測で一往復

ゲームなしの試験接続は、画面の「この接続を終了」で先に閉じます。マイクは接続が一つのときだけ会話先を選べます。

Minecraftを終了し、その起動構成の`config/dogido-fabric-client.properties`をコピーして保管してから、`server_base_url`を次に変更します。

```properties
server_base_url=http://127.0.0.1:5056
```

Minecraftを起動し、明るく敵のいない場所で立ち止まって、会話画面にゲームの接続が出ることを確認します。このファイルの変更・再起動は手動で行います。通常版へ戻すときはMinecraftを終了し、保管した設定へ戻してください。

## 確認する発話

| 発話・操作 | 確認すること |
|---|---|
| 「こんにちは、今日も一緒に遊ぼう」 | 認識した自分の言葉と返答が表示され、最後まで聞こえる |
| 「さっきの遊ぼうは、ゆっくり話そうって意味だよ」 | 直前の会話を踏まえて訂正を受け止める |
| 返答中に画面の「返答・音声を止める」 | 音声が止まり、その返答が「取消」になる |
| 続けて短い話を送る | 取り消した返答を最後まで話した扱いにしない |
| 二文以上の返答を聞く | 最初の文から再生し、続きが順に聞こえる。文間が不自然に空かない |
| 一文目と二文目の間に「返答・音声を止める」 | 合成中だった後続の文が後から再生されず、「取消」のままになる |

最初はこの数往復だけで十分です。体感速度は**話し終わってから声が聞こえ始めるまで**を見ます。端末ログにはplanner・本文生成の個別時間も出ます。実機のマイク・認識・発話区切り・音の途切れは、テキストによる自動試験では確認していません。

音声は検査済みの返答を文ごとに合成し、再生中に次の一文を準備します。LLM本文の生成と検査は引き続き完了を待ちます。端末の`audio_sentence_ready`は各文の合成時間、`audio_first_sentence.prepare_ms`は音声準備開始から最初のplayer起動までです。スピーカーから実際に聞こえた時刻ではなく、`dialogue_finished.total_ms`は全再生時間を含むため、返答開始の遅延と区別してください。

パニック・優先警告・10秒以上の観測途絶では通常会話を取り消し、画面に中断理由を表示します。敵の位置・体数の質問は戦闘中でも受け付けます。知識検索は後続段階です。句の保存・指摘の参考保存・読み訂正・保存した句の検索は接続済みです。

## 次の実機チェック：統合した戦闘

Rustサーバーを終了して再起動し、更新を反映します。接続先は5056のままです。共有MLXとVOICEVOXはそのまま使います。まず検証用ワールドで次を確認します。

1. 単独ゾンビを見つけたとき、悲鳴・敵名・方向が途切れず聞こえる。
2. 敵を見ながら「ゾンビどこ？」「敵は何体？」と聞く。入力拒否にならず、現在の方位・距離・個体数が返る。
3. ゾンビを2体、3体へ増やし、同種の数と、スケルトンを含む種類別の報告を聞く。
4. 警告中に別の未視認の敵音が入っても、前の視認警告が不意に切れない。逆にクリーパーの導火や背後の奇襲は優先される。
5. 撃破と、その場から離れた場合で反応が区別され、戦闘後に通常会話へ戻れる。
6. 警告や方向回答の途中で向きや敵数が変わっても、読み始めた台詞は最後まで聞こえる。次に「ゾンビどこ？」と聞けば最新の位置を答える。

ボス固有反応と聴覚の反復は自動比較済みです。最初の実機確認で全ボスを用意する必要はありません。音が途中で止まる場合は、画面の中断理由と端末の`warning_queued`、`warning_status`、`audio_interrupt`を確認します。マイク・実スピーカーの結果は自動試験とは別に記録します。

## 環境反応と持ち替えの追加確認

- 暗い場所へ進み、暗所の台詞や呼吸を聞く。明るい場所へ戻ると古い呼吸が止まる。
- 明るさが戻っても読み始めた台詞は最後まで聞こえる。猫などのコメントも、相手が視界から消えただけでは途切れない。
- 暗所でゾンビを見つけても、ゾンビの警告本文が反復観測で途切れない。
- 雷による割込み後、途中だった会話へ戻る。待機中の「敵は何体？」も失わない。
- 猫などに遭遇し、会話が落ち着いた後に反応する。観測から消えた相手の生成中コメントは取り消される。
- ホットバーに剣を置き「剣に持ち替えて」と頼む。剣へ切り替わり、端末に`assist_dispatch`とadapterからの`assist_result`が残る。剣がない場合と、否定した場合は操作しない。

## 川柳相談の戦闘中断と復帰

編集箇所は「上五」「下五」だけでなく、現在の一行を読んで「○○を△△に変えて」と指定できます。音声入力欄で認識された語を確認し、指定した一行だけが未採用案へ変わることを試してください。「最初の行」「最後の句」も使えます。語が途中で分割された場合や「それ」だけの指示を、この確定経路で補作することはありません。

移植と模擬試験が済み、次に実音声・Minecraftで確認する経路です。まず次の項目、その後に単独敵との再開を試します。

- 句の相談中に敵に遭遇し、句を保持して警告を優先する。敵を倒す場合と離脱する場合で復帰の言葉が違う。
- 安堵の音声後に同じ三行が最後まで聞こえ、定型の「続ける？」は付かない。「うん」で相談を続け、「続けない」で閉じる。
- 「いい句だね」または「終了でいいよ」の返事中に敵が来ても、終了した句は安全復帰後に再掲されない。未採用案があるときは先に採否を確認する。
- 未採用の修正案がある場合も保持する。「うん」だけでは採用・保存せず、「続けない」には案の採否を確認する。
- 再掲中に敵が来たら中断し、句を失わない。安全へ戻ってから再掲し直す。

敵が残る間の再開は、囲い等で接近できないゾンビ1体を、3ブロックより遠くで観測して試します。他の敵や被弾がない状態で8秒以上待ち、「句の続きを話そう」と伝えます。自動で再開せず、発話後に三行が戻って相談できることを確認してください。中断中の具体的な「この句の意味を教えて」も対象です。

再開した相談中に敵が近づく、被弾する、敵が増えると、相談を中断して警告へ戻り、現在句・未採用案を保持します。「句に戻らない」や、再開確認前の「うん」だけでは再開しないことも確認します。端末の `workshop_combat_input` で判断結果を確認でき、`/api/v1/rust-dialogue/snapshot` の発話行にある `combat_input_result` には使用providerも残ります。実OS AIの可用性と自然な発話の理解、再開の声が聞こえるまでの時間は、この実機確認で判定します。

## 読み訂正の追加確認

- 「草地の読みはくさち」と伝え、確認の返事を聞く。画面の現在句・未採用案は変わらない。
- 句の相談中に「上五は……」と編集の相談をして、読み辞書の保存として扱われないことを確認する。
- 同じ記憶設定で再接続しても訂正が残る。草地のバイオームで「そうちじゃなくてくさち」と訂正した場合、次の発句の保存材料には許可読み「くさち」と禁止読み「そうち」が入る。

この経路はLLM判定を追加しない。保存結果は `reading_correction` ログと発話行の `memory_outcome` で確認できる。テキスト・模擬音声での検証と、マイクで意図した言葉が認識されるかの確認は区別する。

## 指摘の引き継ぎと保存した句の検索

- 句の意味を尋ねたり具体的な言い方を指摘した後、発話行の `workshop_feedback_outcome` と記憶ルートの `long_term/haiku_lessons.jsonl` を確認する。意味説明への「そうなんだ」では新しい注意が増えず、称賛でも前の注意は消えない。
- 「前の注意はもういらん」で注意を緩める。掛け軸の現在句・未採用案は変わらず、次の発句に古い注意が入らない。
- 「覚えてる句を教えて」「今日の句を思い出して」で保存済みの句を聞く。「雪原の句」などの場所指定も試す。未採用案は検索結果へ混ぜず、採用済みの修正には元句と直しが出る。
- 同じ記憶設定で再接続し、以前の保存済みの句を検索できることを確認する。検索中も掛け軸の正本・案を置き換えない。

検索・解除の結果は発話行の `memory_action` と `memory_outcome` へ記録する。自然な指摘の解釈と実音声の読み上げは、模擬試験とは別に確認する。

## 完成句の直しと自作句の保存

- 掛け軸に句がある状態で、テキスト入力へ `直し: はるのいろ / さくらのはみる / あさひかる` を送る。保存の返事があり、相談が閉じる。元句は上書きせず、同じ接続の `long_term/haiku_revisions.jsonl` に直しが残る。
- 未採用案を作った状態で「今の句を保存して」と伝える。元句の自動保存済みという返事になり、未採用案はそのまま残る。
- `川柳保存: 本文` で自作句を保存し、「覚えてる句を教えて」で呼び出す。自作句は通常会話履歴へ混ぜない。
- 相談中に `こう直して: 一行目 / 二行目 / 三行目` の形式も確認する。マイク入力では認識結果を先に確認し、三行の区切りが認識されない場合は全文保存できたとは判断しない。

保存結果は発話行の `memory_action`・`memory_outcome` に残る。保存失敗時は成功を答えず、現在句と未採用案を残す。

## Rust音声入力の確認

川柳の仕上がりを待たずに、この部分だけ5分程度で確認できます。Rustのサーバーと音声入力を再起動し、音声側の端末に「Rust音声入力」と表示されることを確認します。

1. 「おはよう」「ドギド、聞こえる？」と一文ずつ話す。端末に認識文と「届けた」が出て、返答が一度だけ聞こえる。
2. 少し長い文と短い「うん」を試す。文中の間で分割され過ぎないか、話し終わってからの待ち時間を確認する。
3. こちらが黙ってドギドの返答を聞く。ドギド自身の声が次のプレイヤー発言として送られないことを確認する。
4. 音声入力のターミナルでCtrl+C。停止表示後に同じ起動ファイルを開き、再び一往復できることを確認する。
5. マイクのミュート／解除も試す。機器側の動作によって入力が止まった場合は、`aec_failed`等の理由が表示され、生マイクへ勝手に切り替わらないことを確認する。解除後に音声入力を再起動する。

`capture → stt_started → stt_finished → delivery`はRustサーバー側にも診断として残ります。AECの`aec_started`・`aec_levels`も引き継ぎます。自動試験は合成PCMと模擬Whisperで制御を検証したもので、実マイクやエコー除去の品質確認の代わりにはなりません。

叫声や句相談の場面は、通常プレイ中に起きたときに確認します。これらを再現するために次の移植を待つ必要はありません。

- 「うわああ！」だけと認識された場合、端末に`player_vocalization`が出て、叫声への返答生成が始まらない。「うわああ、びっくりした」のように意味のある言葉が続けば通常の会話になる。
- その後の`voice_situation`は同時点の観測だけを示す。敵や爆発の根拠がなければ原因不明となる。叫声で句を採用・破棄・保存しない。
- 音声診断の`prompt_mode`が、句相談中は`haiku_workshop`、戦闘中断中は`normal`へ切り替わる。安全復帰の句再掲後、または明示的な暫定再開後は専用文脈へ戻る。実際の認識文が前より句の語へ寄りすぎていないかも確認する。

## 終了

マイク用とサーバー用の両ターミナルで、それぞれCtrl+Cを押します。Rust側は会話補助と再生プロセスを回収し、`dialogue_stopped`を表示します。共有のMLXとVOICEVOX本体は終了しません。

## 国語対話から別の話への切替

1. 安全な場所で「きょうの音数を教えて」と話し、国語の返事を最後まで聞く。
2. 2分以内に、名指しせず「明日は家を作りたい」と話す。宛先が不明と判定された場合は返答を保留する。
3. 「ドギド」と呼ぶ。さっきの家の話を引用して確認する音声を、最後まで聞く。
4. 「うん」で元の家の話に答える。確認音声の途中の「うん」ではまだ元の質問を処理しない。
5. 別の試行で「ところで、家を作りたい」または「ドギド、家を作りたい」と話し、保留せず通常会話へ移ることを確認する。

保留の有無はモデルの話題理解も含むため、毎回必ず同じ返事になるとは扱わない。端末の`address_held`、表示APIの`routing_status`と`resolution`を、実際に聞こえた音声と照合する。保留中に敵が来た場合や5分を過ぎた場合は、古い家の話を復活させない。確認待ち中でも「枕詞って何？」や「持ち物を教えて」は、それぞれの質問として処理する。

## 句相談・戦闘中の知識質問

1. 句の意味説明を最後まで聞き、「枕詞って何？」を尋ねる。一般知識に答えても現在句は変わらず、その後の「なるほど」は先ほどの句の説明への相槌として扱える。
2. 一行の未採用案を作り、「川柳の決まりを教えて」と尋ねる。元句と未採用案を保ち、知識の質問だけで採用・破棄・終了しない。「この川柳の意味は？」は現在句の相談になる。
3. 敵の警告が出た後に「枕詞って何？」「ソネットの形式は？」と尋ねる。警告を続け、端末の`knowledge_input_routed`と発言履歴で保留を確認する。敵から離れて安全になり、先行音声が終わると質問順に回答する。同じ質問を再送しても二重回答しない。
4. 別の試行で保留中に停止する。再開・再接続後に古い質問を勝手に読み上げない。音声入力の認識文・端末のturn ID・実際の音声を合わせて確認する。

ここは模擬通信で検証済みですが、実マイク・Minecraftでの確認はまだです。

## 戦闘前の会話へ戻る

1. 安全な場所で、建てたい家や集めたい材料について数往復話し、返答を最後まで聞く。
2. 敵との戦闘を挟み、安全に戻って警告・安堵が終わった後、「さっきの話の続き」と話す。戦闘前に話した内容に沿って返るか確認する。
3. 別の試行では国語の質問をしてから戦闘を挟み、同じように続きを求める。聞き返しがあった場合は、何について尋ねていたかが保たれるか確認する。
4. 返答の途中で敵が現れた場合、最後まで聞けなかった説明を、すでに聞いた前提で続けないか確認する。

退避分は戦闘後の既定3回の新しい会話入力まで使い、その後は通常の直近履歴へ戻ります。履歴が渡ること・期限・取消は模擬試験で確認済みです。実モデルの再開の自然さと実際の聞こえ方は、この実機確認で判断します。
