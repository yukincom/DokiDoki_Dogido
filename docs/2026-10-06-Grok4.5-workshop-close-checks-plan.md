# 修正計画: workshop 終了が台詞だけ閉じて内部が開いたまま残る

> 当時のレビュー・検討記録です。現行の実装方針は [AGENTS.md](../AGENTS.md) と各機能の最新仕様を参照してください。

**日付**: 2026-10-06  
**作成**: Grok 4.5 (xAI)  
**状態**: 2026-10-07、P0 の `checks` 欠落補完を実装済み。単独の終了が成立しなければ、再試行せず元の返答本文を使い、本文がなければ無言にする。P1 の再試行プロンプト変更は採用しない。P3 は保留。以下の再試行案は過去の検討記録。  
**確認**: Rust単体488件とworkshop模擬HTTP15件が成功。追加の入出力6例で、欠落時はモデル呼出し1回で終了、不正値・根拠不一致・否定時は終了しないことを確認。全体試験は別件のポータル辞書期待値不一致1件で停止。実Minecraft・実音声は未確認。  
**症状**: 「相談はここで終わり」等で終了したように返事するのに、HUD／内部状態は open のまま。

---

## 1. 結論（原因）

報告どおり。**終了意思の失敗ではなく、使わない欄 `checks` の欠落で操作契約が落ち、再試行が会話へ誘導された結果**である。

| 段 | 何が起きたか |
|---|---|
| 1 | モデルは `close_workshop` と終了 evidence を正しく返す |
| 2 | 操作経路の schema が `checks` を required にしている |
| 3 | `inactive` 既定で欠落欄を埋める処理があるが、**`checks` が含まれていない** |
| 4 | `checks:missing` → `schema_contract_error` → `finalize` に入らず終了しない |
| 5 | retry 指示が「同じ相談の会話を続けて」「普通の返答は action と speech だけ」と誘導 |
| 6 | 再回答が `respond`＋締めの台詞になり、会話経路で受理。内部は open |

`inspect` 以外の操作（特に `close_workshop`）にとって `checks` は意味を持たない。空配列でもよい欄の欠落だけで、正しい終了が棄却されている。

### P0 だけで「完全解消」と言える範囲（限定）

P0（`inactive` に `"checks": []`）で解消できるのは、次に限る。

> **`checks` の欠落だけが原因で、正当な終了（`close_workshop`＋十分な終了 evidence 等）が契約エラーで棄却される経路**

次までは「解決済み」と言わない。

- 別理由でモデルが締め台詞付き `respond` を返す一般問題  
- 終了根拠が否定・引用・疑問などで操作自体が不成立な場合  
- retry 文面の誘導ミス単体（それは P1）  
- HUD／内部が閉じない他原因全般  

P0 は門番の穴の一つを塞ぐ。症状全体の万能薬ではない。

---

## 2. 現行コード上の根拠

### 2.1 操作契約が `checks` を必須にしている

`dogido-rust/src/workshop_validation/assets.json` の agent step schema `required` に `checks` がある。

### 2.2 欠落は `inactive` で埋める設計だが、`checks` が無い

`workshop_validation/mod.rs` は操作系 payload に対し:

1. `ASSETS["inactive"]` を土台にする  
2. モデル出力で上書きする  
3. そのあと `contract::errors` を取る  

現行 `inactive` のキー:

- `close_after_action`, `close_evidence`, `findings`, `line_reference`, `line_proposal`

**`checks` は含まれない。**  
そのためモデルが `checks` を省略した `close_workshop` は、土台マージ後も `checks:missing` になる。

### 2.3 会話経路は別検証で通りやすい（inspect 含む）

`respond` / `explain` / `ask` / `compare` / `inspect` / `show_current` / `unrelated` は、**`inactive` マージより前に** `conversation::handles` → `conversation::validate` へ入る。

そのため:

- 会話系は操作用の全 required を要求しない  
- **`inspect` も操作系の inactive 補完を通らない**  
- P0 で操作系に空の `checks` を補っても、inspect の「検査項目が必要」という仕様は維持できる  
- inspect 試験では、`checks` 欠落・空配列の拒否も確認する（P0 が inspect を緩めたことにしない）

### 2.4 retry 文面が操作修復より会話継続を促す

`workshop_prompt/templates.json` の `retry`:

- 「同じ相談の会話を続けてな」
- 「普通の返答は action と speech だけでええで」
- その後に「編集・採用・終了のときだけ必須入力を揃えよ」

欠落が `checks` のような**操作に使わない欄**でも、モデルは「じゃあ respond で締めの一文」へ逃げやすい。

### 2.5 方針との衝突

`AGENTS.md` はおおむね次を要求している。

- 普通の相談は使わない項目の不備で棄却しない  
- 操作は原文 evidence 等をコード検証してから実行  
- 操作検証失敗時は対象を保持してモデルへ戻す（終了意思そのものを捨てて会話化する意図ではない）

今回は「終了 evidence は足りているのに、使わない `checks` で操作全体を落とし、retry が会話化を誘導」している。

## 3. 修正方針（推奨）

判断ロジック（いつ閉じるか／evidence 閾値）は変えない。  
**門番の穴と、再試行の誘導文だけを直す。**

### P0 — `inactive` に操作で使わない既定を足す（本命・最小）

`assets.json` の `inactive` へ少なくとも:

```json
"checks": []
```

を追加する。

意図:

- 既存設計（欠落欄は inactive で埋める）に乗る  
- **操作系**の `close_workshop` 等で、使わない `checks` の省略が致命傷にならない  
- inspect は会話経路のため inactive の影響を受けない（§2.3）  

併せて確認:

- schema の `required` に残り、操作に不要な欄が inactive 漏れしていないか（今回の直接原因は `checks`）  
- 明示された不正な `checks` 値を、補完や削除で通してしまわないこと（§P2）

### P1 — retry 文面を「形式不足の修復」に寄せる（操作不成立とは分ける）

詳細は `docs/2026-10-06-Grok4.5-workshop-retry-prompt-p1-plan.md`。

要点だけ:

- **形式不足**（欠落・型・使わない欄の missing 等の `schema_contract_error`）→ 同じ操作を直して再提出  
- **操作自体の不成立**（終了根拠が否定・引用・疑問、unsafe evidence、followup 失敗など）→ 既存どおり操作を止めて相談へ戻す（`prepare_conversation_retry` 等）。ここに「同じ操作を再出力」を当てない  
- `templates.json` の retry だけでなく、`CONVERSATION_PROTOCOL`（`workshop_runtime.rs` 冒頭）の「実行できない理由が返ってきたら……説明・相談を続ける」と逆向きの指示が残らないか整合確認  

### P2 — 回帰試験（必須）

受理だけで終わらせない。少なくとも次を固定する。

1. **`close_workshop` が `checks` キー無し**でも、他の必須と安全な終了 evidence があれば受理され、**内部状態と HUD が `closed` になるまで**確認する（`accepted` と完了を混同しない）  
2. **`checks` 省略は補完してよいが、明示された不正値は消して通さない**（不正 enum／型崩れ等は引き続き拒否）  
3. **`inspect`**: `checks` 欠落・空配列は拒否。必要な検査項目付きは従来どおり  
4. P1 後: 形式不足の close 失敗が、retry 誘導だけで respond＋締め台詞の open 残留にならないこと（経路の切り分けは P1 詳細計画）

既存の close＋`checks:[]` 試験に加え、**キー欠落**と **不正値拒否**と **HUD closed** を足す。

### P3 — （任意・後続）操作と会話の required を action 別に分ける

長期的には schema の `required` を action 別に分ける方がきれい。  
今回ログの直接原因（`checks` 欠落による正当終了の棄却）は **P0 で塞げる**。respond すり替わり一般や文面誘導は P1。P3 は別 PR。

## 4. やらないこと

- 終了判定を `fixed_praise` や語句正規化に戻す  
- 「締めの speech ならコードが close する」意味先読みを足す  
- 期待値だけ緩めて「open のままでも speech が締めなら成功」にする  
- 無関係な workshop リファクタや facade 追加

## 5. 実装順（Codex 向け）

P0 と P1 は混ぜず分割してよい。P0 だけの完了条件は「checks 欠落経路」に限定する。

```text
【P0】
範囲: workshop_validation の inactive と関連試験のみ。
1. assets.json の inactive に "checks": [] を追加
2. close_workshop + checks キー欠落 → 受理し、内部/HUD が closed になるまで確認
3. checks の明示不正値は拒否のまま
4. inspect の checks 欠落・空配列拒否を確認（会話経路のため inactive の影響を受けない）

完了条件（P0）:
- checks 欠落だけが原因で正当な close が棄却される経路が消える
- 「respond の締め台詞問題全般が解消」とは主張しない

【P1】別計画 docs/2026-10-06-Grok4.5-workshop-retry-prompt-p1-plan.md
- 形式不足と操作不成立を分けた retry 誘導
- CONVERSATION_PROTOCOL との整合
- prepare_conversation_retry と衝突させない
```

## 6. 検証観点

| 確認 | 期待 |
|---|---|
| validation: close + checks キー無し | accepted → その後の runtime／模擬で **HUD/内部 closed** |
| validation: close + 不正 checks | 拒否（補完で消して通さない） |
| 模擬 HTTP: 終了発話（欠落経路） | `accepted` と `state==closed` を分けて待つ |
| inspect: checks 欠落／空 | 拒否 |
| inspect: 正当な checks | 従来どおり |
| 会話 respond | 従来どおり action+speech で可 |

実機: checks 欠落まわりが直ったあとも、「相談はここで終わり」を一度見る。別原因の respond すり替わりは P1／実モデル確認の領域。

---

## 7. 一言

終了の意味理解は成功していた。直接壊していたのは **使わない `checks` の欠落を inactive が埋めないこと**。  
P0 はその経路だけを塞ぐ。retry 誘導や操作不成立時の相談差し戻しは P1 で、経路 B と衝突させない。
