# 2026-10-11 Gemma 26B: 本文JSON版と候補提出API版の比較

> この文書は同日朝の比較時点の記録。その後、JSON方式＋公式QAT由来モデルを採用した。[採用と確認記録](2026-10-11-qat-json-adoption.md)。

同じ常駐26Bモデルで、変更前の本文JSON実装と、現在稼働中のnative function calling実装を比較した。今回の3場面・各3回では、旧JSON版の方が検査通過率と所要時間で良かった。API化だけで発句品質・速度が改善したとは言えない。

## 条件

- 実モデル: `isetnefret/Huihui-gemma-4-26B-A4B-it-qat-q4_0-unquantized-abliterated-mlx-4Bit`。8080のlistener PID 3403、cwd、起動引数、起動ログとモデルcacheを確認した。`default_model`というAPI名だけでは判定していない。各試行の前後もPID・起動引数が一致した。
- 旧JSON版は前回作業の変更前バックアップから実験ディレクトリへ復元してビルド。API版は現在の実装からビルド済みの同じdebug profileの独立発句exampleを使用した。本体を旧版へ切り替えていない。
- 保存済みの草地・坑道・雪斜面の材料を固定し、seed 101 / 202 / 303、各方式9回。各組の実行順を交互にし、逐次実行。各方式1回の事前実行（草地・seed 7）は集計外。
- 初稿temperature 0.6、再生成0.3、出典評価0.0。候補300 tokens、評価512 tokens。各呼出し20秒、一句180秒、最大再生成6回。HTTP記録で全試行の設定・入力の一致を検証した。
- seedは同一場面の両方式で初稿・再生成・評価ごとの同じ連番規則で付与。MLX-LMのローカル実装はseed指定時に非batch経路を使うため、実ゲームの並行処理時の待ち時間とは区別する。共有モデルのcacheは消していない。
- 計時は発句exampleの開始から終了まで。候補生成・修正・出典評価・辞書helperを含む。見どころ生成、TTS、ゲームへの配送、記憶保存は含まない。実行は10:04:58〜10:07:57 JST、計測対象は10:05:11以降。
- これはプロンプトの役割・指示と検査結果の渡し方も含む実装前後の比較。転送形式だけを独立変数にした比較ではない。

## 失敗と品質の内訳

1. **坑道の3回は出典評価の矛盾で停止。** API版の下五修正案「いしがひかるや」に対し、評価が `pass` なのに `atom_ids: []` を返した。既存の単独再照合でも同じ組合せとなり、`grounding_unavailable` で終了した。JSONの外形は読めており、採用可能な根拠が欠けたための棄却。評価自体は両方式共通の本文JSON経路。
2. **API版の雪斜面では候補応答が3件空。** 各試行の最初の修正で `finish_reason=length`、出力300 tokens、messageは `role` のみとなり、本文もtool callも受け取れなかった。コードは `chat_completions response content is empty` として次の修正へ進んだ。残る27/30件は指定したnative候補呼出しとして受理され、tool結果のID対応は18往復で一致した。何の生成途中で上限になったかはこの応答だけでは分からない。
3. **雪斜面の初稿は一行の欄へ一句分を入れた。** APIの外形は正しくても、三つの各欄に長い句が入り音数を大幅超過。空応答・根拠重複・下五の字余りも経て5回の修正が必要だった。
4. **採用された句にも不自然さがある。** JSON版には「たまごそそぐ」、API版には金床の材料から「かねとこのつめさ」が残った。意味・語の妥当性を同じモデルが評価する弱さが見える。これは出力を読んだ限定的な所見であり、盲検での品質評価ではない。API版の各場面はseedを変えても同じ結果になり、独立した多数の句を試せたとは言えない。

## 今朝の実ゲームと解釈の範囲

本体は昨夜02:31起動のAPI版（PID 66742）のまま。10:01の実ゲーム発句も `source_atoms_slots_v3_native_candidate` で、最後の下五「ときをわすれて」が7音となり許容最大6音を超え、再生成6回で不採用だった。失敗通知「まとまらんかった。。。」の音声完了までログに残った。この実ゲーム事例は比較用18試行には含めていない。

今回の検証区間には、本体ログの発句LLM開始・通常会話LLM開始の検出イベントは0件だった。ただし共有モデルへの他アプリの全要求を排除・監視したわけではなく、完全な専有環境の性能測定ではない。

前夜のE4Bは最終API構成で1回のみの失敗記録で、同じ18試行を行っていない。さらに今回はHuihui版・4bit量子化でモデルの由来も異なる。したがって26B化だけによる改善率・速度比は算出しない。今回分かったのは、この26B・固定3場面では旧JSON実装が現API実装より少ない呼出しで多く採用されたこと。

次に切り分ける候補は、一行欄と一句の混同、候補空応答、出典評価の `pass` と空根拠の矛盾。通信形式の優劣と断定する前に、人物像・出力内容・評価条件を揃えた追加比較が必要。今回、本体実装・モデル設定・サービスの再起動は行っていない。
