## A. Rust らしからぬ処理（unidiomatic）

### A1. Python 真偽文字列変換が4系統 — **duplicate · high**

同じ `Null→"None" / true→"True" / false→"False"`:

| 場所 | 関数名 |
|---|---|
| `reaction_leaf/prompts.rs` | `pystr` |
| `haiku_prompt/blocks.rs` | `string` |
| `knowledge/minecraft.rs` | `python_text` |
| `chat_catalog.rs` | `text`（配列・dict まで Python `repr` 風） |

プロンプト用のレガシ表記が型境界になっていない。一本化するか、そもそも bool/null を JSON のまま渡す契約へ寄せたい。

### A2. `planner::python_json` が横断シリアライザ名 — **naming · high**

`PythonSpaces` + `python_json` が `workshop_prompt` / `haiku_prompt` / `chat_prompt` / `light_plan` / `language` / `haiku_bridge` 等から呼ばれる。

- 「planner 専用」ではない  
- 「一時的な Python 互換」でもない（本番プロンプト整形）

名前が責務を偽る。`compact_json` / `prompt_json` 等へ改名し、`planner` 配下から共有モジュールへ移すのが自然。

### A3. `workshop_editing` がほぼ全面 `Value` + `json!` — **high**

隣接の `workshop_edit::Pending` は型付きなのに、編集エンジン出口（`edits.rs` 等）は匿名 JSON。

- キー typo が実行時まで残る  
- clone が増える  
- 「Rust に移した」感より「JSON を Rust で組み立てている」感が強い

### A4. カタログ群が `LazyLock<Value>` + `include_str` — **high**

例: `entry_catalog.rs` の `HOSTILE`、`world_catalog`、`environment/ambient/catalog.rs`、`catalog_editor::ENTRIES`、`companion_prompt::TEXT`。

静的データなのに毎回 `["label"].as_str()`。serde 構造体／enum へ落とすとコンパイル時に欠落を潰せる。

### A5. ホットパスの不要 clone — **med**

- `workshop_combat_input::Analysis::parse(&Value)` が `payload.clone()` 前提  
- `dialogue/mod.rs` 周辺の履歴行・repair のフィールド単位 `.clone()` 密集（観測は `Arc` 化済みと対照的）

### A6. その他（low〜med）

| 項目 | 内容 |
|---|---|
| `companion_prompt` の `unwrap` | キー欠落でパニック。型化すれば起動時に潰せる |
| `ambient/catalog::enum_text` | Serialize→JSON→文字列。列挙表示には過剰 |
| `reaction_leaf/sanitize` の `digit-ranges.json` | 「Python digit table」としてロード。定数の方が意図が明確 |
| `memory_api::read` → `Value` | `View` enum があるのに出口が無型 |

## B. 名称が不適切 / つながって見えない

### B1. `haiku_bridge::Helper` — **naming · disconnected · high**

コメントは「辞書 token の IPC」。実 spawn 先:

- `haiku_tokens.py`（発句）
- `workshop_helper.py`（相談）
- `combat_input_helper.py`（戦闘分類）
- `tts_unidic_adapter.py`

実体は **任意 Python worker の寿命管理**。`haiku_` 接頭辞が配線を隠す。`python_worker` / `stdio_helper` の方が正直。

### B2. `workshop_helper.py` — **naming · duplicate · med**

中身は UniDic `tts_shared_tokens.handle` の薄いラッパのみ。workshop の parser / validator は import しない。  
`haiku_tokens.py` と同役なのに別名。読者は「workshop 論理が Python に残っている」と誤読しやすい。

### B3. `workshop_edit` vs `workshop_editing` — **naming · disconnected · med**

| モジュール | 役割 |
|---|---|
| `workshop_edit` | CAS / `Pending` / reading・surface |
| `workshop_editing` | パターン編集エンジン |

一連のドメインなのに名前が並立。Python 時代の層分割の残りに見える。

### B4. `reaction_leaf::sanitize` が共通床 — **naming · med**

通常会話（`chat_validation`）や workshop validation が `reaction_leaf::sanitize` に依存。  
パスは「反応専用」なのに横断ユーティリティ。`text_guard` / `speech_sanitize` 配下の方が正しい。

### B5. `compat` モジュール — **naming · low**

コメントは「現行仕様であり互換層ではない」。名前は捨て候補に聞こえる。  
中の `is_python_whitespace` / `json_truthy` も Python 語彙のまま（仕様として残すなら `text_rules` + 中立名）。

### B6. 化石コメント — **dead · naming · med**

現行と矛盾する記述が残る。

- `planner/mod.rs`: 「既存Pythonが作る同一文脈で比較する」
- `chat_validation.rs`: 「Python retains observation projection...」
- `world_catalog.rs`: `NarrationMixin` / `WorldAnalysisMixin`
- `precipitation.rs`: `WorldAnalysisMixin._precipitation_context`

Python 本体削除後も、エージェントが「まだ Python 正本がある」と判断する餌になる。

## D. 「これも Rust の方がいい」／二重

### D1. 戦闘分類の契約二重 — **duplicate · should-be-rust · high**

- Python: `dogido_server/combat_input_contract.py` の `validate_payload`
- Rust: `workshop_combat_input::Analysis::parse`

端末 AI SDK 接続は Python に残してよい（方針通り）。  
**採否の最終所有者は既に Rust** なので、schema／confidence／evidence の正本は Rust 一系統に寄せ、Python は「生レスポンスを渡すだけ」にできる。

### D2. UniDic ラッパが3本 — **duplicate · naming · med**

`haiku_tokens.py` / `workshop_helper.py` / `tts_unidic_adapter.py`  
方針上 Python 残存は妥当。問題は **同役ラッパの分裂と誤名**。1エントリ＋op 分岐、または共通スクリプト名に揃えたい。

### D3. 人格・状況 JSON が `dogido_server/llm/` 配下 — **disconnected · med**

Rust が `include_str!("../../dogido_server/llm/...")` で取り込む。  
実行時所有者は Rust なのに、パスが旧 Python パッケージ。  
`data/prompts/` や `dogido-rust/assets/` へ移すと「Python 本体の一部」誤認が減る（ビルド結合も明示的になる）。

### D4. Chrome/Web ポリシー境界 — **should-be-rust · low〜med**（方針付き）

検索開始判断は Rust、URL／公開性ポリシーは Python。文書通りだが、ポリシー変更時は二箇所。中長期で Rust 側 DTO に閉じたい候補。

## 一言

本体の Python 削除は効いている。次に痛いのは「まだ二系統ある」ことより、**Rust の中に残った Python の言葉と形**（`pystr` / `python_json` / `haiku_bridge` / Mixin コメント / 空 pyc）。  
そこを改名と型化で落とすと、Codex も後方互換を増やしにくくなる。
