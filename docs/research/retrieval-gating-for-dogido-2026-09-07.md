# ドギドの検索開始条件：文献と実測の比較

2026-09-07。調査・提案であり、検索条件やモデル設定は変更していない。対象は `language_dialogue` の独立テキスト経路。本体・Minecraft・音声の試験ではない。

## 結論

現時点の第一候補は「意味が確定した国語の質問には安価なローカル検索を行い、Webだけを質問に必要な情報の不足で選択する」。全質問に別のLLM判定を追加したり、全文を何度も生成して多数決したりする方式は先に採らない。

「確信度80%未満」などの共通最適値は見つからない。モデル、世代、資料、質問の分布、検索の費用によって適した条件が変わる。特にドギドでは、検索回数だけでなく子どもの画面を切り替える負担もある。

Qwen3.6-35B-A3B・MLX混合量子化・非思考モード・日本語児童対話・Google AI概要という組合せを直接検証した研究は、今回確認した資料にはない。以下の提案は文献の原則とドギドの実測からの推論であり、改善済みの精度や速度ではない。

## 1. モデルと世代を分けた比較

TARGの掲載先は[著者の業績一覧](https://haibinling.github.io/publication-selected.htm)でも確認。初稿と改訂稿には題名や実験設定の変更があるため、主に2026年4月のv2を参照した。Know Before You Fetchは査読済みとして扱わない。

### ドギドの実際の条件

- 前回15問の実モデル：`mlx-community/Qwen3.6-35B-A3B-4bit-DWQ`。キャッシュのsnapshot IDは `73c707af4243243b18193444467872d20cff9399`。
- 公式の構造は総35B・活性3BのMoE。256専門家中8個と共有専門家を使用する。活性3Bを「知識量もdense 3B相当」、総35Bを「dense 32Bと同じ性能」とは扱わない。[公式モデルカード](https://huggingface.co/Qwen/Qwen3.6-35B-A3B)
- ローカルconfigを確認すると一律4bitではなく、MLP等4bit／注意機構等8bitの混合。`model_type=qwen3_5_moe` は構造名で、モデルIDの3.6と矛盾する証拠ではない。
- `llm/client.py` とキャッシュのテンプレートで `enable_thinking=False` を確認。独立試験の解釈・回答はtemperature 0。公式の非思考モード推奨値は0.7であり、公式評価条件と同一ではない。これだけで不具合の原因とは断定せず、設定も変更していない。[公式生成条件](https://huggingface.co/Qwen/Qwen3.6-35B-A3B#usage-guidelines)
- 計測端末はApple M4 Max、64 GiB。論文の別ハードウェアの秒数を、このMacの予測値にはしない。

世代差を考慮しても「新しいから自己判断も正確」とは結論できない。前回は資料を渡してもTNTの文字を取り違え、未質問の不足を挙げた。一方、文字比較や述語などには答えた。モデル能力、指示文、検索対象、説明範囲が混ざった結果であり、モデル単体の能力の上限を測った試験ではない。

## 2. 数値から分かること

### 段階化は有効でも、毎回1回検索より必ず速くなるわけではない

Adaptive-RAGのTable 1ではGPT-3.5のF1は適応型50.91、複数回型50.87。時間は1回型を1とした相対値で1.46対3.33、検索・生成段階数は1.03対2.81。多段処理を省く効果はあるが、単純な1回型より適応型の方が時間は長い。T5分類器の正解率にも限界があるため、分類器を足せば正しく分かれるとはいえない。[本文Table 1・6](https://aclanthology.org/2024.naacl-long.389.pdf)

### 資料が十分かと、モデルが正解できるかは異なる

Sufficient Contextは「この質問に答えを構成できる情報があるか」を評価する。115件の人手ラベルでGemini 1.5 Proの1例付き評価器は正解率93.0%。これは回答正解率や全領域での保証ではない。資料が十分でも読解に失敗し、不十分でも内部知識で正解する場合があった。回答を控える選択による精度改善は、答えた問題の割合と一緒に読む必要がある。[§3–5](https://arxiv.org/html/2411.06037v3)

ドギドへの適用：資料の限界を全て「検索が必要」にせず、質問の解決に必要かを判断する。誤字・読み違いは別の失敗として記録する。

### 固定の検索率・固定の自己申告値は移植しない

Self-RAGの既定の検索閾値0.2は、専用学習した検索トークンの確率に対する値である。「回答が20%しか確かでない」という意味ではない。[§4](https://arxiv.org/html/2310.11511v1)

TARGのTable 1ではQwen2.5-7B／TriviaQAのMargin設定が検索率33.8%、EM62.2。毎回検索はEM57.6、検索なしは60.8。改善はあるが、毎回検索の方が検索なしより悪い資料条件でもある。7B/8Bの閾値や「検索70〜90%削減」という要約値を、公式の狭い国語DBにそのまま当てはめない。ドギドのJSON記号・関西弁の語尾などの生成確率を、知識の確実さと混同する可能性も別途評価が要る。[§4・Table 1](https://arxiv.org/html/2511.09803v2)

### 同じQwen系列でも、判定を挟むと速くなる場合と遅くなる場合がある

Know Before You FetchのTable 4は、実測した各処理時間を使う費用モデルで、評価集合上の正解率一致点を比較している。Qwen3-8Bは常時検索107.5msに対し二分岐136.1ms（約27%増）、32Bは346.5msに対し319.9ms（約8%減）。本番の対話をそのまま通した測定や、検証用データで選択済みの閾値の速度ではない。

別のTable 3では、検証用データで閾値を選ぶとTriviaQAで検索率65.2%、正解率77.0%（常時検索78.5%）。NQ/MS MARCOでは約97〜99%検索を選んだ。検索を何割まで減らせるかは問題分布次第である。[§5.4・5.6](https://arxiv.org/html/2606.29959v1)

## 3. ドギドのDB規模と処理時間

### 実際に検索している範囲

正規化データ全体は7データセット・45,168レコード。ただし語彙選定表を含み、45,168件の語義辞典があるという意味ではない。

今の独立対話経路では、手整備の国語4分野65件、補足カード8件、必要に応じて常用漢字2,136件・学年別配当1,026件を参照する。収集した800文型や大きな基本語彙表全体を常に意味説明へ渡す経路ではない。1回に渡す事実の上限は10件。一般語義を網羅する辞書ではないため、ローカルで0件でも「モデルも知らない」とはならない。

## 4. この規模での提案と概算

### 最初に比較する設計

1. 質問対象・観点・曖昧さを既存の解釈で確認する。会話だけで確認すべきことをWebへ送らない。ただし資料名や辞書の版が未指定というだけで、一般的な説明まで必ず止める規則にはしない。
2. 意味が確定した国語質問では、今の軽いローカル検索を使う。相槌、冒険へ戻る発話、既存説明の単なる言い換えは新しい検索と分ける。
3. 既存の回答生成で「質問への短い答え」「それを支える資料・一般知識」「答えに必要だが欠けた情報」を区別する。追加のLLM呼出しを必須にしない。
4. Webは、答えを変える具体的な不足、確認すべき新しい事実、本人の検索希望に使う。主題に近いだけの余談、網羅していない語義、モデルが勝手に足した説明の不足では開かない。
5. 最初は1回の検索で子どもに渡し、概要がなくても検索結果を使う。リンク先は子どもが戻って説明した内容に必要なものから読む。新しい疑問や明示の続行があれば次の検索を認め、対話全体を1回に固定しない。

これは自己申告を盲信する方式ではない。コードが問いとの対応・重複・状態を管理し、実モデルの判定を試験で評価する。ただし、項目が埋まったことだけで意味的に正しいと保証しない。必要な不足をうまく区別できなければ、検索候補のときだけ短い確認判定を追加する案と比較する。

### 内部知識の扱いは別の要因

今の「factsの範囲だけ」という指示は、モデルが知っている一般知識まで使わせない。これを変えずに検索判断だけ改善する条件と、基本的な語義・既知の文法を内部知識でも説明できる条件は、試験を分ける。学年・表の数値・稀な語源等の根拠が必要な情報と、既知の規則を子どもの例に当てはめることも区別する。内部知識の使用を資料由来と偽って記録しない。

「資料限定の指示で不明と答えた」ことは、Qwenがその内容を知らない証拠ではない。一方、制限を外せば正しく答えるという証拠もまだない。

### 速度の損益（推定）

前回15問は検索要求7件、そのうち不要／時期尚早が4件。仮に4件を減らし、1件のWeb費用を先の実測平均5.143秒と置けば、全質問平均で約1.37秒分のWeb待ちを削減できる。これは同じ15問・MCP経路へ切替後という仮定で、追加読解・子どもの操作・新しい回答の長さは含まない。

全15問へ、現在の回答生成に相当する約1.99秒の判定を追加すると、この削減より費用が大きくなり、平均約0.62秒遅くなる計算になる。短い分類なら同じ2秒とは限らないが、実測前から無料ともみなせない。追加判定は必要な候補だけに限るか、既存生成へまとめるのが第一候補。

一般形は「追加判定時間 < 減らせる検索の割合 × 検索を含む後続処理時間」。ただし速度だけで採否を決めず、誤答と必要な検索の見逃しも比較する。ローカル検索の費用は1回平均約0.075秒なので、同じ理由で全問への重い事前判定は割に合いにくい。

前回の人手評価による3/15件は、現在の資料限定条件での検索候補数であり、「Web率20%が最適」という意味ではない。内部知識を使える範囲が変われば、特に一般語の比較で必要な検索数も変わりうる。

## 5. 最適点を決める最小限の次の試験（未実施）

- 既存15問は回帰用に残す。加えて未使用の日本語質問30〜50件程度から始める。これで汎化精度を保証するのではなく、候補の違いと失敗の種類を把握する。
- 資料に直接答えがある／規則を例へ適用／本当に外部情報が要る／質問が曖昧／言い換え・訂正を分ける。ゲーム由来の語の有無だけでは分けない。
- 現行Qwen3.6・同じ量子化・同じ生成条件を固定し、まず現行方式と「既存生成内で必要な不足だけ判断」を比較する。語句の例外表を増やさない。
- モデル能力の切り分けは同じ質問を資料なし／適切な資料ありで比較する。ただし資料なし条件に「資料以外を使うな」は付けない。閾値改善と内部知識の利用許可を同時に変えて、どちらが効いたか不明にしない。
- 正解率だけでなく、答えられた割合、不要な検索、必要な検索の見逃し、不要な聞き返し、LLM呼出し数、検索回数、初回応答と最終回答の時間を記録する。新たな「分からない」を増やして見かけの精度を上げない。
- 条件を調整する問題と最後に評価する問題を分ける。検索率自体の目標は固定せず、必要な検索を維持しながら無駄と遅延が小さい条件を選ぶ。

モデル変更・別量子化・思考モードへの変更は別の比較条件。導入や重い学習を先に行う必要はない。既存モデルで上の切り分けをした後に、能力不足が残る箇所だけ別モデルを検討する。
