# 周辺観測をドギド基準へ移す

状態: **実装・自動検証・本線mainへの統合に加え、実機への導入・本体起動・Minecraft接続を確認。実モデルの返答と感覚の実機評価はこれから。**

ユーザー指定の範囲は、観測基準をドギドへ移し、現在の視認情報を先に提示する変更まで。会話履歴の方式・人格・質問の配置・呼び寄せ・生成回数を変更しない。初期実装では実機テストの準備ができた段階で知らせ、ゲーム・本体・モデルを再起動しなかった。その後、ユーザーの「対応するModを導入して、実機テストできる状態にして」という依頼により、下記の導入と起動確認を行った。

## 既存実装と変更範囲

[第一段階](2026-10-13-body-vision-phase1.md)で身体基準になったのは、自分の姿勢とowner一人の可視性まで。周辺モブ・ブロック・場所・匂い・音はplayer由来だった。`observer`の表記変更だけでは取得基準は変わらない。

既存のBody APIで検証した身体の位置・目・向きから、adapterの既存collectorが使う観測者を作る。身体用とplayer用で可変の保持状態を分け、採取・分類・強度の規則は共通化する。身体Modの視野・ガラス・壁内視点の処理も共有し、別の視認規則を複製しない。身体の位置・HP・移動・食料取得の挙動は維持する。

| 情報 | 基準・扱い |
|---|---|
| 周辺の視認 | ドギドの位置・目・向き・視野・見通し |
| 場所・バイオーム・明るさ・水中・局所の天候 | ドギドの地点。高さも身体の値を使う |
| 匂い | ドギドを受け手に距離と強度を計算。playerの所持品はplayer地点の匂い源 |
| 音 | 発音時の身体地点へ届く実音。原時刻と一意な番号を保持 |
| HP・所持品・乗車・指差し・被弾・操作結果 | player本人の状態として保持。ドギド自身の感覚へ混ぜない |

## 取得と配送

- Body API／Fabric payloadはv5、身体Modは0.6.0。HTTPの`body_observation`はv3へ更新する。旧版をplayer情報で補完しない。
- 身体姿勢・owner視認は同じserver snapshotの実測を使う。周辺視覚・環境は、検証済みの身体姿勢からclient worldを読む。`basis=body_pose_client_world`として、serverで同時採取した値と区別する。
- 既存の`body_observation.sample.senses`へ身体の感覚を載せる。新しいHTTP endpointやモデル呼出しを追加しない。
- 身体の不在・失効・倒れている状態・未ロード領域は理由付き未取得。playerの視界や匂いで代用しない。
- body／owner／epoch／dimensionの変化と観測喪失で身体側の保持状態を失効させる。playerの状態や会話履歴は保持する。
- client worldの読み込み範囲を確認し、観測のためにchunkを生成しない。件数・距離・ray数・通信サイズに上限を設ける。切り詰めと観測済み空、未取得を区別する。

### 音の取得範囲

通常のserver音と爆発音は、serverでの発音時に身体地点への到達を検査する。音の距離規則はMinecraftのsound定義を使い、同じ音をsnapshotで再取得しても時刻や保持期限を更新しない。後から近づいて、過去の音を新たに聞いた扱いにしない。

雨・雷・焚き火・ポータル等にはclient側で発生する音もある。既存の実音取得から、実座標がある非relative音だけを身体地点で検査して補う。UI・音楽・位置をplayerで代用した音は使わない。clientで発生しない範囲の音まで取得したとはみなさず、ブロックの存在から音を合成しない。音の記録がないことを周囲の無音の証拠にしない。

## Rustと会話入力

既存の`body::State`がowner・次元・世代・順序・鮮度を検証したsnapshotだけから、判断一回分の感覚用コピーを作る。元のplayer座標と戦闘情報は上書きせず、観測者の高さを独立して参照する。

通常会話、匂いへの明示質問、感覚の短期保持、環境反応の生成と再照合、川柳材料を同じ取得基準へ揃える。指差し先はplayerの話題として保持し、ドギドの現在視認に自動合流させない。

構造化された観測の先頭へ現在の視認を置き、環境・匂い・音を続ける。位置、向き、前回値も保持する。履歴のメッセージ分離・質問を末尾へ動かす案は今回実施しない。

## 検証と導入準備

復旧基準はmainの`1408d43`。既存の他作業の変更を保存・識別し、分離した作業場所で実装・ビルドする。レビュー済みの今回の変更だけをmainへ統合する。

1. 二者を別の位置・向きに置いた入力で、モブ・ブロック・場所・高さ・匂い・音が身体側から取得されることを検査する。
2. body不在・失効・世界／世代変更・未ロードでplayer情報へ戻らないことを確認する。
3. 現在視認の先頭配置、判断時の不変コピー、元のplayer戦闘・所持品・指差しの意味が保持されることを検査する。
4. 音の発音時距離、再取得の重複、時刻、件数・通信上限、視覚の遮蔽／ガラス／壁内／対象ブロック命中を検査する。
5. Rust全target・Clippyと両Javaプロジェクトのtest/buildを通し、adapterへBody APIクラスが二重同梱されないことを確認する。
6. 本体・身体Mod・adapterの導入用成果物とハッシュを保存し、実機で確認する手順を記録する。自動検査を実機確認済みとは表記しない。

実機では二者を離して片方だけから見える対象を用意し、playerだけ回転／ドギドだけ回転、匂い源・音源への接近と離脱、身体の消失・再接続を確認する。その後、履歴を保った会話で入力値と返答を照合する。


## 提供された研究と、次の切り分け候補

2026-10-13にユーザーから関連調査が提供された。以下は原論文の要旨（DynaMemは本文も）で研究対象を確認した範囲。ドギドでの原因や改善効果を示す実験ではなく、今回の実装範囲を増やす根拠にはしない。

| 研究 | 参考にする区別 | ドギドでの未検証範囲 |
|---|---|---|
| [Concord](https://arxiv.org/abs/2610.05281) | 観測と変更可能な情報源を結び、古い文脈を更新・注記・除外する | ファイル更新の評価から、ゲームの会話履歴への有効性は断定できない |
| [PlanFence](https://arxiv.org/abs/2609.03340) | 最新情報の保持と、古い情報から作った計画の有効性は別。行動の依存元を照合する | 動的な方位発話を発話直前に再確認する設計は、適用案として別途評価する |
| [STALE / CUPMem](https://arxiv.org/abs/2605.06527) | 明示的な否定がなくても以前の記憶が失効し得る。更新情報の検索と行動への適用を分ける | 会話記憶の評価であり、身体のリアルタイム制御を検証した結果ではない |
| [DynaMem](https://arxiv.org/html/2411.04999v2) | 新しい空間観測で動的な位置の記憶を更新する | ドギドではゲームのID・座標を使えるため、画像からの復元系を導入する必要性は未判断 |

今回の実機テストは、まず取得元を揃えた版で現在入力と返答の一致を確認する。それでも失敗する場合は、同じ現在状態・同じ指示で履歴あり／なしを比較する。観測tick、生成に使った不変コピー、生成時刻、実際の表示／発話時刻を照合し、入力時点の誤りと配送までの遅延を分ける。履歴の自動書換えや、新しい発話取消規則は今回追加しない。視野外・遮蔽・未ロードは対象の消滅を証明しない。
