# ModernBERT-Ja向け依頼5分類データ v1

**日付:** 2026-10-13

**正本:** [dev_tools/request_classifier](../dev_tools/request_classifier/README.md)

## 目的と対象

入力が「現在の敵情報」「今の剣持ち替え」「今の乗り物呼び戻し」のどれを求めるかを、一般会話・その他の依頼と分けるための初期データ。試すモデルは [ModernBERT-Ja](https://huggingface.co/sbintuitions/modernbert-ja-30m) を想定する。今回はモデルの取得・起動・学習は行わない。

現在の本体では敵方角が `combat/queries.rs`、剣が `assist/intent.rs`、乗り物が `assist/horse_recall/intent.rs` に入口を持つ。実験資産は本体から独立した `dev_tools/request_classifier/` に置いた。稼働中の設定、プロンプト、これらの入口、実行処理には変更を加えていない。

「どこにいるかな」の文字列に含まれる「いるか」が、現在の敵方向判定でカタカナをひらがなへ揃えた「イルカ」と部分一致する。種名らしい文字列を見つけても、それだけで敵を尋ねているとは限らない。[実機ログの分析](2026-10-13-body-vision-live-analysis.md) と [後続の確認記録](2026-10-13-body-observation-origin.md) を、このデータの動機としている。分類が合っても、現在の位置を正しく答えられることは別の検証事項。

## 5分類

正本の整数IDは [labels.json](../dev_tools/request_classifier/labels.json)。`not_request`以外は広義の依頼とし、質問、禁止、取消も含める。

| ID | ラベル | 含めるもの | 例 |
|---:|---|---|---|
| 0 | `not_request` | 挨拶、感想、報告、自分の予定、引用の紹介、明示的な独り言 | 「剣の模様がかっこいい」「友達が『馬を呼んで』と言ってた」 |
| 1 | `enemy_information` | 現在の敵の有無・位置・方角・距離・数・可視性を尋ねる依頼 | 「敵いる？」「ゾンビはどこ？」「まだ二体いる？」 |
| 2 | `equip_sword` | 今、本人の手持ちを剣へ変更する依頼 | 「剣に持ち替えて」「剣にしてくれない？」 |
| 3 | `recall_mount` | 今、既存の乗れる動物をここへ呼び戻す依頼 | 「乗ってきた馬を呼んで」「そのロバをこっちへ」 |
| 4 | `other_request` | 上記以外の質問・依頼、禁止・取消・予約、解決できない依頼 | 「私はどこ？」「剣にしないで」「あとで馬を呼んで」 |

`enemy_information`は「敵」という語の有無では決めない。敵種への現在の質問や、直前に敵だと分かる対象への省略質問を含む。「モブ」「そいつ」だけで敵とはみなさず、イルカ・村人などについての普通の質問は`other_request`。現実の視認や存在を言語だけで確定せず、質問の意図を分類する。

範囲は有無・位置・方角・距離・数・可視性に限定する。「ゾンビの残りHPは？」「敵を倒して」など、現在の敵に言及していても範囲外の質問・操作は`other_request`。

`recall_mount`は馬だけに限定しない。現在の乗り物支援が対象とする動物を含む。友達の馬や実在不明の個体を呼ぶ発話でも、呼び戻しの**意図**はこの分類にする。所有権・候補・UUID・最新状態・実行可否は既存コードで確認する。犬・猫・ボート・ドギド自身を呼ぶ依頼は`other_request`。

### 注釈の順序と境界

1. 引用の内外と、訂正・取消の範囲を読む。
2. 最後まで有効な本人の依頼を特定する。
3. 省略対象が直前の会話から一意に解決できるか確認する。
4. 異なる依頼が複数有効か確認し、5分類へ割り当てる。

| 境界 | 分類の扱い |
|---|---|
| 「さっき敵がいた」／「さっき敵は何体いた？」 | 報告は`not_request`。過去についての質問は`other_request` |
| 「敵はいない？」／「敵の位置は教えないで」 | 前者は敵情報の質問。後者は`other_request`の禁止 |
| 「剣にしてくれない？」／「剣にしないで」 | 婉曲な肯定依頼は`equip_sword`。禁止は`other_request` |
| 「『馬を呼んで』と言っていた」／「『馬を呼んで』を今実行して」 | 引用の報告は`not_request`。引用を本人の依頼として実行させる場合は`recall_mount` |
| 「馬を呼べとは言ってない、昔の話」／「馬を呼ぶのを中止して」 | 意図の説明だけなら`not_request`。実行中止の依頼なら`other_request` |
| 「敵が来たら剣にして」「明日の朝に馬を呼んで」 | 将来や未成立条件での予約は`other_request`。今実行しない |
| 「剣にして。いや、やめて」／「やめて、いや今は剣にして」 | 最終的に有効なのは前者が取消、後者が剣持ち替え |
| 「馬は呼ばなくていい、剣にして」 | 取消を除くと現在有効な依頼は剣持ち替えだけ |
| 「馬を呼んでから剣にして」 | 両方が有効。単一分類で一つを選ばず`other_request`＋確認用注釈 |
| 「それお願い」 | 一意な提案があればその依頼。対象不明・複数候補なら`other_request`＋確認用注釈 |
| 完了報告への「ありがとう」「それでいい」 | 新たな実行依頼ではなく`not_request`。実行前の提案への承諾と区別 |

`needs_clarification`は**依頼カテゴリを一つに解決するための確認**の注釈。第6分類でも学習入力でもない。「その馬を呼んで」の個体識別や、「いま敵はいる？」の観測不足はこのフラグに含めない。5分類モデルだけではこの補助フラグを予測しないため、これを出力できると仮定して本体へ接続しない。

## 件数・分割・出自

| 分割 | not_request | enemy_information | equip_sword | recall_mount | other_request | 合計 |
|---|---:|---:|---:|---:|---:|---:|
| train | 50 | 50 | 50 | 50 | 50 | 250 |
| dev | 15 | 15 | 15 | 15 | 15 | 75 |
| test | 15 | 15 | 15 | 15 | 15 | 75 |
| regression | 5 | 7 | 5 | 5 | 18 | 40 |

合計440件。435件はCodexがこの用途のために作った合成例。5件はユーザーの2026-10-13実機発話の原文だけを抽出した`observed_text`。ログ全体、座標、個体ID、アカウント情報は収録しない。全件をCodexが注釈し、別のCodex担当による独立した読み直しを行った。ユーザーや複数人の人手による正解確認・一致率の測定は未実施。

分割は行単位の無作為抽出ではなく、会話・例文を作ったまとまりの`group_id`単位で固定した。文脈違いの同じ短文、否定・引用・訂正を変えた対は同一分割に置く。各分割には同じ分類を別の言い回しで表した例が必要なので、意味の類似が一切ないことを保証する設計ではない。

同じ提案への承諾・拒否・別依頼も収録した。たとえば剣への持ち替えを提案された後でも、最新の発話が「敵の数を教えて」なら`enemy_information`になる。履歴だけでラベルが決まる偏りを避けるため、train/dev/testそれぞれにこの対照を置いた。学習時にtrain内の行順をシャッフルしても、分割自体は維持する。

検査では、groupの分割間混入、同一入力、表記だけを変えた同一の現在発話の分割間混入を拒否する。表記比較はNFKC・英字小文字化・カタカナのひらがな化・空白／句読点除去を使う。**モデル入力の原文は変えない。** 同一分割内では、現在発話が同じでも文脈が異なれば別例として保持する。

### 「いるかな」の回帰セット

`regression-001`〜`005`が抽出原文。特に今回の3発話は次のとおり。

| ID | 原文 | 注釈 |
|---|---|---|
| regression-001 | さあて！今度はどこにいるかなーー？？どこかなー？？ | 文脈を含まない原文だけでは主語未確定。other_request＋確認 |
| regression-002 | さあて！今度はわたしはどこにいるかなーー？？どこかなー？？ | 自分の位置の質問。other_request |
| regression-003 | さあて！わたしはどこにいるかなーー？？どこかなー？？ | 自分の位置の質問。other_request |

元の実会話の文脈は再構成していない。`regression-001`の確認フラグは原文だけをモデル入力にするこのデータの注釈であり、元の会話でも対象が不明だったという意味ではない。

敵主語の「いるかな」、実際のイルカへの質問、馬の名前が「イルカ」、引用・独り言も同じ回帰群に入れた。既知の失敗から作った回帰セットは、未知入力への汎化性能を示す最終評価とは分けて集計する。

## JSONLと学習入力

各ファイルはUTF-8、1行1JSON object。スキーマv1のフィールドは次のとおり。

| フィールド | 型・用途 |
|---|---|
| `id` | 分割名＋3桁番号。評価結果の照合に使う |
| `group_id` | 分割をまたがせない作成単位 |
| `text` | 現在のユーザー発話の原文 |
| `context` | 古い順の直前会話。最大4発話。各要素は`role: user/assistant`と`text`。空なら文脈なし |
| `label` | 5分類の正解文字列 |
| `needs_clarification` | カテゴリ解決に確認が必要かという補助注釈 |
| `tags` | 否定、引用、省略などの評価用注釈 |
| `source` | `synthetic`または`observed_text` |
| `rationale` | 正解理由。教師入力には含めない |

`dataset.py`の`model_example(row)`が唯一の入力整形関数。過去会話を`履歴:`、現在発話を`現在のユーザー発話:`の後へ置く。返す`text`だけをtokenizerへ渡し、`labels`を教師値とする。分類名・理由・タグ・分割情報・確認フラグを入力に含めない。

```python
# リポジトリルートから使用。モデルや追加ライブラリを読み込まず入力を確認できる。
from dev_tools.request_classifier.dataset import read_splits, model_example

splits = read_splits()
train_examples = [model_example(row) for row in splits["train"]]
```

この初版は短い発話と短い履歴を対象にしている。後続の学習で最大token数を決める際は、長い履歴だけを削り、現在発話を落とさない。主評価では文脈付きのこの入力形式を使い、現在発話だけの評価は文脈依存性を見る補助比較にする。

## 確認方法と今後の評価

READMEの2コマンドでデータ全件と検査器の全6テストを確認する。`data_report.json`に件数、タグ数、出自、文脈あり件数、確認用注釈数、最大入力文字数、各JSONLのSHA-256を保存した。データを意図的に変更した際は再レビュー後、`--write-report`でレポートを更新する。

検査器は、group混入・表記違いの混入・同じ入力への矛盾ラベル・曖昧な依頼を即時操作にする不整合を拒否することも、壊したコピーを使って確認する。意味ラベルの正しさを機械検査だけで保証するものではない。

この変更の対象は独立したデータ・整形・検査だけなので、本体のRust/Fabric試験や実Minecraftでの動作試験は実行していない。既存の「いるかな」誤判定そのものの修正は、まだ本体に反映していない。

学習に進む際の評価方針:

- trainだけで学習し、学習回数や棄却閾値はdevだけで選ぶ。testを見て選び直さない。
- 設定を固定してからtestのmacro-F1、分類別precision/recall、混同行列、二値の依頼判定を報告する。
- 正解が剣／呼び戻し以外なのに、そのどちらかへ流す率を別に出す。両操作間の取り違えも混同行列で確認する。
- 否定・引用・省略、確認が必要な例、自分の位置の質問を部分集計する。regressionの成績は別表で示す。
- これは均等に作った小規模な合成データ中心の初版。実際の会話頻度、音声認識の誤り、長い履歴での性能は測れない。表記揺れ例は音声の実収録ではない。
- 最終評価も設計時に読まれた合成例であり、独立した実ログの未知評価ではない。運用判断には新たな未使用の実入力で確認する。

今回の通過条件はデータの整合性であり、ModernBERT-Jaの精度・速度・誤操作防止の合格ではない。本体に入れる場合も、分類結果から直接実行せず、所有・対象・現在性・入力世代・実行結果の既存検証を維持する。
