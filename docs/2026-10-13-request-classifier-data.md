## 目的と対象

入力が「現在の敵情報」「今の剣持ち替え」「今の乗り物呼び戻し」のどれを求めるかを、一般会話・その他の依頼と分けるための初期データ。試すモデルは [ModernBERT-Ja](https://huggingface.co/sbintuitions/modernbert-ja-30m) を想定する。v1.7のデータ整理ではモデルの取得・起動・学習を行っていない。

現在の本体では敵方角が `combat/queries.rs`、剣が `assist/intent.rs`、乗り物が `assist/horse_recall/intent.rs` に入口を持つ。実験資産は本体から独立した `dev_tools/request_classifier/` に置いた。稼働中の設定、プロンプト、これらの入口、実行処理には変更を加えていない。

「どこにいるかな」の文字列に含まれる「いるか」が、現在の敵方向判定でカタカナをひらがなへ揃えた「イルカ」と部分一致する。種名らしい文字列を見つけても、それだけで敵を尋ねているとは限らない。[実機ログの分析](2026-10-13-body-vision-live-analysis.md) と [後続の確認記録](2026-10-13-body-observation-origin.md) を、このデータの動機としている。分類が合っても、現在の位置を正しく答えられることは別の検証事項。

## 5分類

正本の整数IDは [labels.json](../dev_tools/request_classifier/labels.json)。`not_request`以外は広義の依頼とし、質問、禁止、取消も含める。

| ID | ラベル | 含めるもの | 例 |
|---:|---|---|---|
| 0 | `not_request` | 挨拶、感想、報告、自分の予定、引用の紹介、独り言、実行を求めない冗談 | 「剣の模様がかっこいい」「友達が『馬を呼んで』と言ってた」 |
| 1 | `enemy_information` | 現在の敵の有無・位置・方角・距離・数・可視性を尋ねる依頼 | 「敵いる？」「ゾンビはどこ？」「まだ二体いる？」 |
| 2 | `equip_sword` | 今、本人の手持ちを剣へ変更する依頼 | 「剣に持ち替えて」「剣にしてくれない？」 |
| 3 | `recall_mount` | 今、既存の乗れる動物をここへ呼び戻す依頼・間接的な乗馬希望 | 「乗ってきた馬を呼んで」「そのロバをこっちへ」 |
| 4 | `other_request` | 上記以外の質問・依頼、禁止・取消・予約、解決できない依頼 | 「私はどこ？」「剣にしないで」「あとで馬を呼んで」 |

`enemy_information`は「敵」という語の有無では決めない。敵種への現在の質問や、直前に敵だと分かる対象への省略質問を含む。「モブ」「そいつ」だけで敵とはみなさず、イルカ・村人などについての普通の質問は`other_request`。現実の視認や存在を言語だけで確定せず、質問の意図を分類する。

範囲は有無・位置・方角・距離・数・可視性に限定する。「ゾンビの残りHPは？」「敵を倒して」など、現在の敵に言及していても範囲外の質問・操作は`other_request`。

`recall_mount`は馬だけに限定しない。現在の乗り物支援が対象とする動物を含む。友達の馬や実在不明の個体を呼ぶ発話でも、呼び戻しの**意図**はこの分類にする。所有権・候補・UUID・最新状態・実行可否は既存コードで確認する。犬・猫・ボート・ドギド自身を呼ぶ依頼は`other_request`。

### 通常受付と対応範囲外

平常のワークショップ中の句の感想・推敲・再読・採否は、専用の対話が入力を持つため本データの対象外。進行中の復唱・読み上げ練習も、通常会話と専用学習状態を区別できない合成例は保留した。通常会話から新しく「一句詠んで」と頼む入口、一般的な単発の知識質問、引用の報告は含める。句や練習という語の一致で除外・ルーティングする規則は作らない。実際の受付はコードの状態によって決める。

機能外でも自然に頼みうる操作や情報照会は`other_request`のまま残し、`unsupported_request`タグで別集計する。たとえばモブの残りHP、過去の冒険の位置検索、剣以外の持ち替え、運搬・建築・攻撃の代行、将来の自動実行。タグは5分類とは別のレビュー注釈であり、モデル入力に含めず、モデルが実行可否を判断できると仮定しない。

現在の候補や直近の騎乗情報が使えることと、過去の全乗車・冒険を永続保存していることを区別する。候補にない色や過去体験からassistantが個体を確定する文脈は、ユーザー自身の説明や名札を根拠にする形へ修正した。ユーザーが色で呼び戻しを頼む自然な発話は保持し、特定できるかは実行側へ委ねる。

### 注釈の順序と境界

1. 引用の内外と、訂正・取消の範囲を読む。
2. 発話全体で本人が今実現したいことを読む。驚き・状況確認が後の依頼の理由や前置きになっている場合は、独立した依頼として機械的に分割しない。最後まで有効な依頼と、相棒への間接的な希望を特定する。
3. 省略対象が直前の会話から一意に解決できるか確認する。
4. 別々の回答や操作を求める依頼が複数有効か確認し、5分類へ割り当てる。疑問符や動詞の数だけで複数依頼としない。

| 境界 | 分類の扱い |
|---|---|
| 「さっき敵がいた」／「さっき敵は何体いた？」 | 報告は`not_request`。過去についての質問は`other_request` |
| 「なんだあれ・・・？敵？剣出してくれる？」／「今ゾンビの声した？念の為、剣に変えといてくれる？」 | 敵への気付きが剣の依頼の前置き・理由になっている。ともに`equip_sword` |
| 「いま、敵がいなかった？」 | 今の周囲の敵の有無を確かめる`enemy_information`。否定過去形だけで過去の記録への質問にしない |
| 「のりたいなー！馬にのりたいなー？」 | 相棒に向けた今の乗馬希望を、馬を呼んでほしいという間接的依頼として`recall_mount`にする |
| 「乗り物を出してくれ！ええと・・・飛ぶ・・・ほらあれだよあれ！！」 | 特徴と指示語でガストを指した呼び出し依頼として`recall_mount`。名前が出てこないことだけで依頼カテゴリを不明にしない |
| 「いそうなのにいない？」 | 今回のユーザー指定では思案・独り言として`not_request`。疑問形だけで敵情報の依頼にしない |
| 「ベンツを回してくれ」 | Minecraftの相棒に馬を呼んでほしいという比喩として`recall_mount`。字面の自動車だけで分類しない |
| 「代わりにトイレに行ってきてくれる？」 | 実行を求めない冗談として`not_request`。実行できない操作依頼をすべて非依頼にする基準ではない |
| 「ライター持ってる？」 | 火打石の所持確認として`other_request`。本体の現在の言い回し判定が拾えるかと、発話の意図を分ける |
| 「敵はいない？」／「敵の位置は教えないで」 | 前者は敵情報の質問。後者は`other_request`の禁止 |
| 「剣にしてくれない？」／「剣にしないで」 | 婉曲な肯定依頼は`equip_sword`。禁止は`other_request` |
| 「『馬を呼んで』と言っていた」／「『馬を呼んで』を今実行して」 | 引用の報告は`not_request`。引用を本人の依頼として実行させる場合は`recall_mount` |
| 「馬を呼べとは言ってない、昔の話」／「馬を呼ぶのを中止して」 | 意図の説明だけなら`not_request`。実行中止の依頼なら`other_request` |
| 「敵が来たら剣にして」「明日の朝に馬を呼んで」 | 将来や未成立条件での予約は`other_request`。今実行しない |
| 「剣にして。いや、やめて」／「やめて、いや今は剣にして」 | 最終的に有効なのは前者が取消、後者が剣持ち替え |
| 「馬は呼ばなくていい、剣にして」 | 取消を除くと現在有効な依頼は剣持ち替えだけ |
| 「馬を呼んでから剣にして」「敵の場所を教えてから剣に替えて」 | 個別の操作・回答が両方有効。単一分類で一つを選ばず`other_request`＋確認用注釈 |
| 「それお願い」 | 一意な提案があればその依頼。対象不明・複数候補なら`other_request`＋確認用注釈 |
| 完了報告への「ありがとう」「それでいい」 | 新たな実行依頼ではなく`not_request`。実行前の提案への承諾と区別 |

乗り物を呼ぶ意図が読み取れる場合は、対象の名前を思い出せないことと依頼カテゴリの不明を区別する。「飛ぶ乗り物」「あれ」と特徴・指示語で表した今回の例は、ユーザーの意図どおりガストの呼び戻しに分類する。どの個体を呼べるかは既存の候補選択と実行前確認に委ねる。

`needs_clarification`は**依頼カテゴリを一つに解決するための確認**の注釈。第6分類でも学習入力でもない。「その馬を呼んで」の個体識別や、「いま敵はいる？」の観測不足はこのフラグに含めない。5分類モデルだけではこの補助フラグを予測しないため、これを出力できると仮定して本体へ接続しない。

### 今回合意した「県」の扱い

MinecraftのSTTでは「剣」が高頻度で「県」になるというユーザー報告に基づき、今回の学習例では「県」を「剣」と解釈する。モデル入力には「県」の原文をそのまま渡す。これはこの利用場面の意味解釈であり、本体のSTT補正コードや実行条件を変更するものではない。

語の解釈と依頼の有無は別に読む。「県を出して」は持ち替え、「県に変えないで」は禁止、「県の見た目が好き」は感想となる。「県！」だけは現在の操作依頼か単なる言及かを決めきれないため、今回の追加から保留した。現在の入力形式は音声・文字の入力元フィールドを持たないので、MinecraftのSTTという合意を前提とする作例である。一般的な都道府県の話や、入力元別の補正性能を保証しない。

ユーザーが正解を指定した9例は、Minecraftの相棒との会話における期待分類として採用する。「ジョーク」という注記や正解理由をモデル入力へ付け足さない。冗談でも馬を呼ぶ意図がある「ベンツを回してくれ」と、実行を求めない「代わりにトイレに行ってきてくれる？」を区別する。今回の独り言・比喩・冗談の正解はこの用途での注釈であり、同じ本文があらゆる会話で常に同じ意図になるとは保証しない。初版の、文脈から分類不能と確定できる`other_request`＋確認の例は維持する。

2026-10-13のユーザー訂正を受け、「明示の操作語がない」「疑問が複数ある」「過去形を含む」ことだけで意図を分断しない基準に改めた。相棒に向けた現在の乗馬希望は呼び戻しの意図として扱う。昔の思い出や将来の夢、明示的な独り言・引用は、時制・話者・発話目的に応じて区別する。`recall_mount`は既存の乗れる動物を呼ぶ意図であり、新しい個体を生成する操作を追加する意味ではない。

分割は行単位の無作為抽出ではなく、会話・例文を作ったまとまりの`group_id`単位で固定した。文脈違いの同じ短文、否定・引用・訂正を変えた対は同一分割に置く。各分割には同じ分類を別の言い回しで表した例が必要なので、意味の類似が一切ないことを保証する設計ではない。

同じ提案への承諾・拒否・別依頼も収録した。たとえば剣への持ち替えを提案された後でも、最新の発話が「敵の数を教えて」なら`enemy_information`になる。履歴だけでラベルが決まる偏りを避けるため、train/dev/testそれぞれにこの対照を置いた。学習時にtrain内の行順をシャッフルしても、分割自体は維持する。

v1.6では過去のユーザー発言を含む2〜4発話の履歴付き例を63件追加し、複数発話の履歴付きは1→64件になった。同じ最新発話が、数発話前の依頼によって剣・呼び戻し・敵情報・その他へ分かれる8例を一つのgroupにまとめた。追加例の最大入力長は保存済みの30M tokenizerで76 tokenと確認し、既存の128 token枠に全文が収まる。入力の切り詰めはしていない。この段落の件数はv1.6の作成時点であり、v1.7ではワークショップの4件をこの追加分から除外した。

検査では、groupの分割間混入、同一入力、表記だけを変えた同一の現在発話の分割間混入を拒否する。表記比較はNFKC・英字小文字化・カタカナのひらがな化・空白／句読点除去を使う。**モデル入力の原文は変えない。** 同一分割内では、現在発話が同じでも文脈が異なれば別例として保持する。

## JSONLと学習入力

各ファイルはUTF-8、1行1JSON object。スキーマv1のフィールドは次のとおり。

| フィールド | 型・用途 |
|---|---|
| `id` | 分割名＋3桁番号。評価結果の照合に使う |
| `group_id` | 分割をまたがせない作成単位 |
| `text` | 現在のユーザー発話の原文 |
| `context` | 古い順の直前会話。最大4発話。各要素は`role: user/assistant`と`text`。空なら文脈なし |
| `label` | 5分類の正解文字列 |
| `needs_clarification` | カテゴリ解決に確認が必要かという補助注釈 |
| `tags` | 否定、引用、省略、`unsupported_request`（未対応依頼）などの評価用注釈 |
| `source` | `synthetic`、`observed_text`、`user_example` |
| `rationale` | 正解理由。教師入力には含めない |

`dataset.py`の`model_example(row)`が唯一の入力整形関数。過去会話を`履歴:`、現在発話を`現在のユーザー発話:`の後へ置く。返す`text`だけをtokenizerへ渡し、`labels`を教師値とする。分類名・理由・タグ・分割情報・確認フラグを入力に含めない。

```python
# リポジトリルートから使用。モデルや追加ライブラリを読み込まず入力を確認できる。
from dev_tools.request_classifier.dataset import read_splits, model_example

splits = read_splits()
train_examples = [model_example(row) for row in splits["train"]]
```

この初版は短い発話と短い履歴を対象にしている。後続の学習で最大token数を決める際は、長い履歴だけを削り、現在発話を落とさない。主評価では文脈付きのこの入力形式を使い、現在発話だけの評価は文脈依存性を見る補助比較にする。

## 確認方法と今後の評価

READMEの2コマンドでデータ全件と、データ検査9件・評価補助4件・採否台帳3件の計16テストを確認する。`data_report.json`に件数、タグ数、出自、文脈あり件数、確認用注釈数、最大入力文字数、各JSONLのSHA-256を保存した。データを意図的に変更した際は再レビュー後、`--write-report`でレポートを更新する。

検査器は、group混入・表記違いの混入・同じ入力への矛盾ラベル・曖昧な依頼を即時操作にする不整合を拒否することも、壊したコピーを使って確認する。意味ラベルの正しさを機械検査だけで保証するものではない。

この変更の対象は独立したデータ・整形・検査だけなので、本体のRust/Fabric試験や実Minecraftでの動作試験は実行していない。既存の「いるかな」誤判定そのものの修正は、まだ本体に反映していない。

学習に進む際の評価方針:

- trainだけで学習し、学習回数や棄却閾値はdevだけで選ぶ。testを見て選び直さない。
- 設定を固定してからtestのmacro-F1、分類別precision/recall、混同行列、二値の依頼判定を報告する。
- 正解が剣／呼び戻し以外なのに、そのどちらかへ流す率を別に出す。両操作間の取り違えも混同行列で確認する。
- 否定・引用・省略、確認が必要な例、自分の位置の質問を部分集計する。`unsupported_request`の43件と、その補集合`ordinary_scope`の711件は分けて集計する。後者も個体解決・回答内容・実行成功を保証する意味ではない。regressionの成績は別表で示す。
- v1.7ではdev/testの入力と一部タグも変更した。旧版の同一IDだけで予測を再利用したり、旧test精度との単純な増減を出したりしない。旧版比較には保存したv1.6を使い、新版の成績は別のデータ版として測る。
- これは均等な初版に選別例を追加した小規模な合成データ中心のセット。v1.7のtrainは分類ごとに95〜141件で、完全均等ではない。実際の会話頻度、音声認識の誤り、長い履歴での性能は測れない。表記揺れ例は音声の実収録ではない。
- 最終評価も設計時に読まれた合成例であり、独立した実ログの未知評価ではない。運用判断には新たな未使用の実入力で確認する。

今回の通過条件はデータの整合性であり、ModernBERT-Jaの精度・速度・誤操作防止の合格ではない。本体に入れる場合も、分類結果から直接実行せず、所有・対象・現在性・入力世代・実行結果の既存検証を維持する。

## 所持確認と現在の本体の対応範囲

「ライター持ってる？」は火打石の所持確認として、ユーザーが`other_request`を指定した。現在の本体はインベントリ全体の種類・個数を受け取り、所持質問と判定した場合に個数順で最大18種類を会話へ渡す。持ち替え操作はホットバー限定。「ライター持ってる？」自体は既存の所持質問条件に入らないが、今回の学習例では所持確認の意図を分類する。持ち物の質問全般を非依頼へ移す変更は行わない。

確認した実装は`PlayerObserver.buildInventory`、`chat_materials/current.rs`の`inventory_summary`生成、`chat_world.rs`の要約処理、`input_policy.rs`と`input-policy.json`の所持質問条件。これはコードの確認であり、実機での「ライター」質問の応答試験ではない。
