# Code Review: `situations.sculk_sensor` と出力コードブロック混入

> 当時のレビュー・検討記録です。現行の実装方針は [AGENTS.md](../AGENTS.md) と各機能の最新仕様を参照してください。

**日付**: 2026-10-03  
**レビュワー**: Grok 4.5 (xAI)  
**対象プロジェクト**: DokiDoki-Dogido  
**方針**: コード変更なし。調査・原因分析・修正方針のみ。  
**報告された症状**: `"situations": { "sculk_sensor": ... }` 周辺がおかしく、出力にコードブロック（\`\`\`）が出る。

---

## 全体サマリー

`reaction_situations.json` の `deep_dark_ominous_sound.situations.sculk_sensor` 自体は **構文も配線も正常** です。テストも状況文の差し替えを正しく検証しています。

コードブロックが混ざる主因は、状況文キーではなく **本番の応答契約 `choice_contract` が禁止例としてリテラル \`\`\`json をプロンプトに埋め込んでいること** です。`prompt_lab` の候補プロンプトではすでにこの表記が除去されており、本番 `companion_prompts.json` だけが取り残されています。

加えて、Python 反応パスと Rust 反応パスで「素のセリフ契約」と「JSON speak/silent 契約」が食い違っており、フェンス付き返答の扱いもパスによって異なります。

---

## 結論（先に）

| 項目 | 判定 |
|---|---|
| `situations.sculk_sensor` の JSON 定義 | 問題なし |
| `ominous_kind` → 状況文の解決 | 問題なし（Python / Rust とも一致） |
| コードブロック混入の本命 | `companion_prompts.json` の `choice_contract` 内の \`\`\`json |
| 副次リスク | Rust `speech_choice::parse` がフェンス非対応 / Python `clean_output` がフェンス JSON を \`\`\` に潰す |
| Python vs Rust の契約差 | 反応 leaf で `speech_contract`（Py）と `choice_contract`（Rust）が分岐 |

## 1. `situations.sculk_sensor` は壊れていない

### 定義（正本）

`dogido_server/llm/reaction_situations.json`:

```json
{
  "event": "deep_dark_ominous_sound",
  "situation": "スカルクかウォーデンの音が聞こえた。",
  "situation_key": "ominous_kind",
  "situations": {
    "sculk_sensor": "スカルクセンサーの作動音が聞こえた。",
    "sculk_shrieker": "スカルクシュリーカーの叫び声が聞こえた。",
    "warden_heartbeat": "ウォーデンの心音が聞こえた。",
    "warden_presence": "ウォーデンの音が聞こえた。"
  }
}
```

- キー名・ネスト・フォールバック用の親 `situation` は整合している。
- 文言にバッククォートやフェンス開始列は含まれない。

### 解決ロジック

**Python** (`dogido_server/llm/reaction_prompts.py`):

```python
situation = row.get("situations", {}).get(
    details.get(row.get("situation_key")),
    SITUATIONS[kind],
)
```

**Rust** (`dogido-rust/src/reaction_leaf/prompts.rs`):

```rust
row["situation_key"].as_str()
    .and_then(|key| d[key].as_str())
    .and_then(|encounter| row["situations"][encounter].as_str())
    .or_else(|| row["situation"].as_str())
```

実測（レビュー時）:

```text
event=deep_dark_ominous_sound, ominous_kind=sculk_sensor
→ situation = 「スカルクセンサーの作動音が聞こえた。」
```

`tests/test_dialogue_character_mode.py` の `test_sound_situations_distinguish_activations_weather_and_completed_screams` も同じ期待値を固定している。

**所見**: 「`sculk_sensor` のラインがおかしい」ように見えるのは、多くの場合 **同じプロンプト塊の中に `choice_contract` の \`\`\`json があり、Markdown / ログビューアがそこからコードフェンスを開いてしまう** ため。`situations` 行自体が壊れているわけではない。

---

## 2. 本命: 本番 `choice_contract` が \`\`\`json を教えている

### 本番（問題あり）

`dogido_server/llm/companion_prompts.json` → `choice_contract`:

> 返事はJSONを一つだけ返してな。**\`\`\`json** みたいなコードブロックや前後の説明文は一切付けんと、{ から始まる生のJSONだけを返してな。…

禁止したい形式を **実物のフェンス開始列で例示** している。多くのモデルは「やるな」と言われた形式をそのまま真似しやすい。

### prompt_lab 候補（すでに修正済み）

例: `dev_tools/prompt_lab/candidates/gemini-a.json` ほか複数候補:

> 返事はJSONを一つだけ返してな。話すときは {"action":"speak",...}、黙っとくときは {"action":"silent",...} や。ほかのキーや前後の説明文は付けんといてな。

こちらには **バッククォート列がない**。ラボ側で既に同じ症状への対策が入っているが、本番正本へ未反映。

### 波及範囲

- Rust 反応 / 共有対話は `companion_prompt::dialogue()` 経由で常に本番 `choice_contract` を載せる。
- `dogido-rust/src/reaction_leaf/fixtures.json` 内にも、埋め込み system 文言として \`\`\`json が大量に出現する（レビュー時カウント: 332）。Markdown や一部ビューアで開くと、後続の JSON（`situations` / `sculk_sensor` 含む）がコードブロック表示に飲み込まれる。

---

## 3. 出力経路ごとの「コードブロック」の出方

症状の見え方は経路で変わる。今回の報告は「全部あり得る」前提で整理する。

### A. Rust 反応 leaf（本番本体寄りの経路）

1. system に `choice_contract`（\`\`\`json 例示あり）
2. user は状況コンテキストの **生 JSON**（`json.dumps` / `serde_json::to_string`）
3. モデルが \`\`\`json ... \`\`\` で包んで返すと、`speech_choice::parse` は `serde_json::from_str(raw.trim())` のみ
4. **フェンス除去なし** → `invalid_contract` → 固定 fallback

対比: `haiku_response.rs` には `strip_code_fence` がある。反応パスだけ未対応。

**結果**: 最終セリフにフェンスが残るより、**パース失敗 → fallback** になりやすい。デバッグ画面や生ログではフェンス付き raw が見える。

### B. Python `DogidoLLM.generate_leaf_text`（互換 / 一部経路）

1. `build_reaction_messages(..., choose_silence=False)` が既定
2. したがって反応は **`speech_contract`（素のセリフ）** を要求
3. それでもモデルが JSON / フェンス付き JSON を返すと、`clean_output` は行分割の結果として **\`\`\` だけ** を拾い得る

レビュー時の実測:

| 生出力 | `clean_output` 結果 | `is_usable_output` |
|---|---|---|
| \`\`\`json\\n{"action":"speak","speech":"センサー反応したで。"}\\n\`\`\` | \`\`\` | False → fallback |
| {"action":"speak","speech":"センサー反応したで。"} | JSON 文字列のまま | False → fallback |
| センサー反応したで。 | そのまま | True |

**結果**: 最終採用文に \`\`\` が残ることは通常ない（usable 判定で落とす）。ただし raw / cleaned ログには \`\`\` が残る。

### C. prompt_lab / Markdown 表示

- system 連結に `choice_contract` を含むため、表示面でフェンスが「開いた」ように見える。
- user 側の `situations` / `sculk_sensor` がその直後に続くと、「あの行がおかしい」ように誤認しやすい。

### D. `/dogido` 発言表示

`docs/dogido-utterance-display.md` より、動的本文は HTML 解釈せず文字列表示。最終確定セリフにフェンスが乗らなければ、ここ単独でコード枠にはなりにくい。

## 4. Python / Rust 契約の非対称（関連バグ）

| | Python 反応 | Rust 反応 |
|---|---|---|
| 関数 | `build_reaction_messages(..., choose_silence=False)` | `companion_prompt::dialogue(mode)` |
| 契約 | `speech_contract`（素のセリフ） | `choice_contract`（JSON speak/silent） |
| パース | `clean_output` + usable/style | `speech_choice::parse` |
| フェンス除去 | JSON 抽出経路にはあるが、leaf 本文経路は弱い | なし（haiku のみあり） |

コメント上は「Rust は speak/silent、Python 互換は plain speech」と分かれているが、**同じ `reaction_situations.json` を共有しつつ契約が違う**ため、ラボ／本番／互換経路で「コードブロックが出る／出ない／fallback になる」がぶれやすい。

`sculk_sensor` は deep dark 反応の代表ケースとしてよく触るため、この非対称の症状が最初に目につきやすい、という位置づけが妥当。

---

## 5. 良い点

- 状況文の正本を `reaction_situations.json` に集約し、Python / Rust が同じファイルを読む設計は明確。
- `situation_key` + `situations` マップで音種ごとの文言差し替えができている。
- prompt_lab 候補がすでに \`\`\`json 除去済みで、本番への反映方針が事実上検証されている。
- haiku 側にはフェンス除去があり、同種問題への対処パターンがリポジトリ内に存在する。

## 6. 修正方針（実装はしない。提案のみ）

優先度順。

### P0 — 本番 `choice_contract` からフェンス例示を消す

`dogido_server/llm/companion_prompts.json` を prompt_lab 候補と同型へ寄せる。

- 「コードブロック禁止」は **バッククォート列を書かずに** 伝える（「生の `{` から始まる JSON だけ」「前後に説明を付けない」）。
- 反映後、`reaction_leaf/fixtures.json` など埋め込み system を再生成し、\`\`\`json 残存をゼロにする。

### P1 — Rust `speech_choice::parse` でフェンス除去

`haiku_response::strip_code_fence` と同等の前処理を `speech_choice::parse`（または `Leaf::finish` 直前）に入れる。

- フェンス付きでも正規 JSON なら speak/silent を採用できる。
- 回帰テスト: \`\`\`json\\n{"action":"speak","speech":"…"}\\n\`\`\` が `Ok(Speak)` になること。

### P2 — Python leaf 側の契約を明示的に揃える

方針をどちらかに固定する。

1. **Rust に合わせて** 反応も `choose_silence=True`（JSON 契約）にし、leaf 後処理で `action/speech` をパースする  
2. **互換 Python は素のセリフのまま** とし、user メッセージが「JSON を返せ」と誤誘導しないよう、契約文と user 形を見直す

現状の「system は speech、user は JSON コンテキスト」は、モデルに JSON 返答を誘発しやすい。

### P3 — `clean_output` のフェンス耐性（Python）

フェンス付き JSON を \`\`\` に潰す挙動はログノイズと誤診断の元。leaf が JSON 契約を採るなら、先に fence strip + JSON extract してから `speech` を取る。素のセリフ契約なら、先頭/末尾フェンス行を捨てて本文行を残す。

### P4 — 観測・再現手順の固定

次を 1 セットで残すと切り分けが速い。

1. `ominous_kind=sculk_sensor` の reaction messages をダンプ（system 末尾に \`\`\`json が含まれるか）
2. モデル raw にフェンスがあるか
3. Rust `finish` / Python `generate_leaf_text` の採用理由（`speak` / `invalid_contract` / `unusable_output` / fallback）
4. `/dogido` 確定発言にフェンスが残るか
