# Minecraft観測の重複取得を解消する計画

2026-10-26。状態: **段階1〜5完了・段階6未着手**。静的監査の基準は `main` の `5274ac1`。実機での取得回数・処理時間は未計測。

## 目的と作業場所

同じ観測周期・同じ対象から同じ事実を取り直している処理を解消する。観測範囲、送信頻度、警告、操作、撮影、現在値と変化の契約を保つ。対象はFabric側の取得と、Rust側の同一入力からの重複した組み立て。

作業は書類フォルダの `DokiDoki-Dogido` の `main` で行う。計画だけを先にコミットし、以下の6段階をそれぞれコード・関連テスト・本書の結果更新を含むコミットにする。各段階の途中では次の段階へ変更を広げない。

開始時は追跡済みファイルに未コミット変更なし。未追跡の `docs/2026-10-23-Grok4.5-CodeReview-compat-deletion-targets.md` は別作業として保持する。`main` は `origin/main` より53コミット先行しているため、今回の履歴は開始点 `5274ac1` から区別する。

## 既存経路と共有の境界

- [WorldObservationFrame](../adapter/minecraft-fabric/src/main/java/dogido/fabric/observation/WorldObservationFrame.java) はworld・周辺ブロックを同じ走査周期内で一度取得している。イベント材料はこの経路を拡張し、並行する観測キャッシュを増設しない。
- [BodyConnection](../adapter/minecraft-fabric/src/main/java/dogido/fabric/body/BodyConnection.java) の `Frame` を通常tickの所有者から各consumerへ渡す。コールバックの登録順に依存して「直前に誰かが取った値」を拾う方式にはしない。
- 同じ対象・中心・範囲・観測時点の元情報を共有する。次tick、ワールド・dimension・owner・body・sessionの変更、操作後、非同期処理後には必要な現在確認を行う。身体の経過時間・期限判定も進める。
- 戦闘JSON全体は共有しない。同じtickでも `endCombat()` の前後では `combat_active_hint` などが変わる。経験値玉や周辺entityなどの取得値と、イベントごとの判断結果を分ける。
- プレイヤーと身体の観測、通常視野と危険確認用視野、視覚と嗅覚、画像画素との対応付けは、それぞれの条件を維持する。
- JSONのコピーにはイベント間の変更混入を防ぐ役割がある。取得回数の削減とコピー撤去を混同しない。

関連仕様: [身体基準の観測](2026-10-13-body-observation-origin.md)、[身体観測の現在値と変化](2026-10-14-body-observation-changes.md)、[位置関係の共通観測](2026-10-15-body-position-observation.md)、[身体と撮影の方針](2026-10-26-look-capture-and-darkness.md)、[嗅覚](smell-policy.md)。

## コミット単位

### 1. 光源・ドア・バイオームの同一処理内の重複を解消

予定メッセージ: `光源とドアの観測を一回の走査へまとめる`

- `LightObservation`: 通常光源の個数と最短距離を一回で集計する。危険確認用光源も、その既存範囲内で一回の集計にまとめる。異なる範囲を一つにして判定を変えない。
- `ShelterObservation`: ドア総数と開いたドア数を一回で集計し、上半分を除く既存条件を保つ。
- `WorldObserver`: それぞれの集計結果を既存のJSON項目へ接続する。
- `SmellObserver`: 一回の `observe` 内で同じ位置のバイオームを使い回す。
- 置き換えた旧走査の呼出し・不要な旧入口も同じコミットで撤去する。

確認: 空の範囲、範囲境界、最短距離、開閉とドア上下、嗅覚の対象バイオームについて、集計値が従来の契約と一致すること。同じ範囲に対する個数・距離用の二重読取りがなくなること。既存のworld・smellテストと関連Javaコンパイル。

### 2. 同じtickのイベントでプレイヤーと周辺材料を共有

予定メッセージ: `同じ観測周期のイベント材料を共有する`

- `WorldObservationFrame`、`EventObservationCapture`、`DogidoClientAdapter` を中心に、必要になった元情報を一度だけ取得する既存の仕組みを広げる。
- 対象はplayer、inventory/hotbar、落下アイテム、look target、直近のブロック破壊、周辺構成など、同じ周期内で不変の入力。playerとinventoryの内部で同じ所持品を読む重複も追う。
- snapshot・接近・音・死亡・爆散・戦闘終了など、すべてのイベント生成入口を同じ材料へ接続する。
- イベント名、sequence、時刻、優先度、視覚・聴覚の採用条件、結果一覧はイベントごとに組み立てる。イベントを省略・統合して回数を減らさない。
- イベントを送らないtickでは、共有のためだけに所持品や周辺アイテムを先行走査しない。

確認: `WorldObservationFrameTest` 等の既存Supplierと呼出し回数の検査を拡張する。同tickに複数イベントがあっても各元情報は一回、次周期では再取得、片方のJSON編集は他方へ混ざらないこと。周期snapshotと緊急イベントの内容・頻度を維持すること。

### 3. 経験値玉とWarden周辺の取得を共有

予定メッセージ: `戦闘観測の周辺entity取得を共有する`

- `CombatObserver` の経験値玉取得を、イベントごとのcombat組み立てから切り離し、同じ周期の材料へ接続する。
- `BossObserver` の毎tickの特殊配置確認とイベント用観測で、同じ中心・半径のクリスタル／TNT取得結果を共有する。player中心と各Warden中心は区別する。
- 共有データの寿命をその周期に閉じる。後から異なる中心・範囲を要求された場合は、それに対応する取得を行う。
- 戦闘開始・終了、追跡中の死亡／爆散などの状態更新は今の所有者と順序を保つ。

確認: 複数イベント、Warden不在・一体・複数体、中心の移動、戦闘終了と別イベントが同tickに起きる場合。元情報を共有しても `combat_ended` が終了後の状態を持つこと。該当する観測テストとcombat模擬通信。

### 4. 通常tickの身体frameを各consumerへ渡す

予定メッセージ: `身体の定期観測を一つのframeへ揃える`

- `DogidoClientAdapter` の通常tickで得た `BodyConnection.Frame` を、感覚、身体操作の完了監視、inspect、撮影側の移動観測へ明示的に渡す。
- `BodyViewCapture` の独立した毎tick取得を統合する。撮影要求がなくても必要な移動・停止の観測は続ける。
- 同じ撮影tick内の診断表示には、すでに得た `observed` を使う。
- `BodySensesCollector` の通常視野と安全視野で、同じ身体entityの検索結果を共有する。視野条件とそれぞれの可視判定は保つ。撮影側などへ同じentityを渡せる場合も、その周期内に限定する。
- pending操作の完了結果は各tickで監視する。別の時点の受付や描画直前の更新まで、tickのframeで置き換えない。
- 切断、dimension変更、身体の消失・入れ替わり、未取得時のクリアも呼出し所有者へ揃える。

確認: 撮影なしの通常tickでは身体APIから一回取得し、同じ周期のconsumerはそのframeを使うこと。次tickの更新、操作結果の到着、未取得、切断・再接続を確認する。`BodyViewMotion`、`BodyViewAfterLook`、`BodyInspectController`、`BodyConnectionAction`、session関連テスト。

### 5. 身体操作受付の二重取得と対象外音の先行取得を解消

予定メッセージ: `身体操作と音観測の不要な再取得をなくす`

- `BodyRequestRuntime` のLOOK_TARGET／LOOK_DIRECTIONで、対象計算と `BodyLookController` の受付照合を同じ取得値から行う。`BodyLookRuntime` の既存入口を整理し、同じ受付内で再取得しない。
- `BodyInspectRuntime` などについても、一回の受付・判断内に残る同じframe／身体entityの再取得を確認して取り除く。
- 発音callbackでは、null・relative音・対象外カテゴリなど、身体情報を必要としない既存の除外を先に行う。通過した音だけ、発音時点に必要な身体情報を取る。除外条件の定義は一か所へ揃える。
- session、owner、dimension、期限、command ID、実行結果との対応を確認する処理は、それぞれの必要な境界に残す。

確認: LOOK_TARGET／LOOK_DIRECTIONの一受付は一回取得、対象外音は身体API取得ゼロ、対象音は従来どおり取得されること。方向・注視・inspectの結果、期限切れ、重複命令、古いcontextを既存テストで確認する。`check_body_requests.py`、`check_body_gaze.py` も実行する。

### 6. Rustで同じ受信入力を重複して組み立てない

予定メッセージ: `同じ受信イベントの身体観測を再利用する`

- `dialogue/observe.rs` で同じ受信イベントから二度作っている `body_runtime::event` を、一回の判断用の値として共有する。採用時点・有効期限と途中の状態更新を確認してからまとめる。
- `environment_latest` を合成した別の入力の投影は、元イベントと同じものとして扱わない。
- `submit`、`turn`、`visual_runtime::Source`、`chat_runtime` の既存経路を追い、受け渡した直後に同じ材料を再構築する箇所を解消する。
- queue待ち、履歴更新、画像待ちの後は、現在の観測・短期履歴・取消世代を使う。Minecraftへの追加要求と、受信済み情報の組み立てを区別する。必要な再構築を減らす目的で、新しい汎用キャッシュや複雑な変更監視を足さない。
- 後半の再構築は削除可能性の監査対象。異なる時点・入力で必要なものは理由を本書へ記録し、同一処理の重複として撤去しない。

確認: 同一受信イベントの投影共有、観測の現在値と未消費の変化、待機中の新規観測・履歴、画像待ち中の変化、失効・取消・古いepoch、入力重複時の抑止。対象Rust単体テストと `check_body_senses.py`、`check_warning_observations.py`、`check_dialogue.py`。

## Gitの進め方

1. 計画だけを `Minecraft観測の重複取得解消計画を記録する` としてコミットする。
2. 各段階の開始時にHEAD・statusを確認する。上の段階が検証済みでコミットされていることを回復点にする。
3. その段階のコード・必要な回帰テスト・仕様／本書の更新をまとめる。APIだけ増やして旧経路を残すコミットや、呼出し元の切替前でビルドできないコミットは作らない。
4. 関連チェック成功後、`git status --short`、未ステージ差分全体、ステージ差分全体、`git diff --check` を確認する。実際に変更したタスク所有のパスだけを列挙してstageし、コミットする。
5. 1→2→3→4→5→6の順で進める。共有ファイルの同時編集を避ける。段階に依存関係があるため、戻す場合は後の段階から逆順のrevertを基本とし、全コミットが独立にcherry-pickできるとは扱わない。
6. 別作業の変更が入った場合は取り込まず区別する。push・tag・履歴書換えはこの計画に含めない。

## 最終確認と完了条件

各段階では対象を絞り、全段階の統合後に全体検証を一度行う。変更・失敗・未解決の懸念が出た場合にだけ追加で実行する。

- Fabric: adapterディレクトリで `./gradlew test build`。既存の身体API依存を使い、配布jarにAPIの複製を混ぜない。
- Rust: リポジトリrootで `./dogido-rust/cargo.sh test --all-targets --locked`、模擬通信で使用するdebug本体を更新、最後に通常起動用releaseをビルドする。
- 模擬通信: 身体感覚・操作・注視、通常対話、環境・警告、戦闘とworkshop中断復帰を、変更範囲に応じた既存 `check_*.py` で確認する。自前の一時service・記憶・ポートを使う。
- 回数の証拠: 既存のfake／Supplier境界で読取り回数を検証する。戻り値だけ一致して内部で再走査している状態を合格にしない。確認のためだけの常駐ログ・監視機構は増設しない。
- 実Minecraft: 通常移動、snapshotと危険イベントの重なり、戦闘終了、ドア・光源、匂い、身体への注視依頼、撮影、音、dimension変更・再接続を確認する。同じ条件で取得回数と処理時間を比較し、数値を取れなければ性能改善量は未測定とする。
- 実機の既存service・Minecraft・Mod配置を操作する際は、起動元・実行中の版を確認し、プレイ中の状態を勝手に停止しない。ビルド済み、配置済み、起動済み、実機確認済みを別々に記録する。

完了条件は、確認済みの重複が除去され、取得元をたどって残る再取得の必要性が説明でき、各コミットがビルド・関連チェックに通ること。自動検証と実機確認を混同せず、未確認の項目があれば明記する。
