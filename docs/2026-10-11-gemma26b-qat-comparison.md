# 2026-10-11 Gemma 26B: Huihui版とLM Studio QAT版

ユーザー指定の[LM Studioモデルページ](https://lmstudio.ai/models/google/gemma-4-26b-a4b-qat)からリンクされている[MLX 4bit版](https://huggingface.co/lmstudio-community/gemma-4-26B-A4B-it-QAT-MLX-4bit)をダウンロードし、常駐8080で比較した。

この固定3場面では、QAT版のJSON方式は9/9採用・全句が厳密5/7/5だった。API方式はHuihui版より中央値が10.421秒から6.188秒へ約41%短縮したが、採用は6/9のまま。QAT版でもJSON方式の方が採用数が多く、中央値も短かった。

## 導入と比較条件

- 新モデル: `lmstudio-community/gemma-4-26B-A4B-it-QAT-MLX-4bit`。固定revision `aa5e2e50376f54254d503276ca2222ea8569b95e`。12ファイル・15,641,263,625 bytesを既存Hugging Faceキャッシュへ保存し、重み3shardとtokenizerのSHA-256を配布元LFS情報と照合した。
- 既存の8080管理APIで登録・切替。旧PIDと起動引数を直前に再照合して停止し、同じ起動スクリプトから新モデルをロードした。MLX/MLX-LMは更新せず、重み・配布config・templateも加工していない。モデル指定以外の起動引数は一致した。
- 稼働確認はlistener PID、起動引数、cwd、ロードログ、実際の短い日本語応答による。`/v1/models`だけでロード済みとは判断していない。ドギド本体5055とVOICEVOXは再起動していない。
- 旧JSON/APIの実行ファイル、固定3場面、seed 101/202/303、交互の順序、候補300 tokens・評価512 tokens、temperature 0.6/0.3/0.0、最大6回の再生成、タイムアウトは[直前のHuihui版比較](2026-10-11-gemma26b-json-vs-native.md)と同じ。各方式1回の事前実行は除外し、新モデルでも各方式9回を実行した。見どころ生成・音声・ゲームへの配送・保存は測定外。
- 両配布物の大枠の量子化設定は4bit / group 64 / affineで一致し、tokenizer.jsonも同じhash。ただしchat_template.jinjaのhashは異なる。重みの改変だけに効果を帰属できず、配布モデル一式の比較とする。
- seed指定でMLX-LMの非batch経路を使い、共有モデルのcacheは消していない。専有環境の本番latency試験ではない。各実装もプロンプトの役割・feedbackを含めて異なるため、JSON/nativeという転送形式だけの効果ではない。

## 残る問題と解釈

- QAT版のAPI候補は12/12回、native tool callとして受理できた。Huihui版にあった候補の空応答3回は今回は出なかった。ただし提出形式が通ることと、句や根拠の検査に通ることは別。
- 坑道のAPI方式は3回とも初回の根拠照合で停止した。下五を `pass` としながら `atom_ids: []` を返し、個別再照合では `assessments` を必要な配列ではなくオブジェクトとして返したため、有効な行評価を取得できず `grounding_unavailable` になった。候補提出に成功しても、後段のJSON評価にはこの問題が残っている。
- 雪斜面のAPI方式は `ゆうぐれのな / きんしょうつめたき / ゆきのさか`（6/8/5）を3回とも採用した。現行の±1音許容には収まるが、金床を表すと思われる「きんしょう」には読みの問題があり、採用をそのまま品質良好とは扱えない。
- 坑道のJSON・seed 202では「ゆらぐひが」を坑道空間、「くろいこころを」を石炭鉱石へ対応させて合格にしていた。9/9は現行検査通過の件数であり、出典対応の意味的な正しさの保証ではない。
- seedを変えても同じ句が多く、QAT版の採用句はJSONが4種類、APIが2種類だった。9回は多様な9場面を意味しない。自然さの盲検評価は行っておらず、モデル全般の優劣やQATだけの因果効果を確定する比較ではない。
