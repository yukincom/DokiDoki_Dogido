## 結論

主な難点は **現行仕様に追従していない試験** と **漢字読みの検証環境不足** である。  
「変更前も失敗」は問題がないという意味ではない。

やることは、期待値だけを緩めることではない。次を同じ変更セットで揃える。

1. 模擬モデルの返答（採用・終了・編集の action を現行どおり返す）  
2. 完了待ち（入力受理 ≠ 終了処理完了）  
3. 辞書の有無（漢字編集が成立する条件を試験が明示する）  
4. 文書（旧「明白な称賛は即終了」などの取り残しを現状に直す）

## 実装・方針上の注意（試験を書くときの前提）

### 採用・終了はモデル選択と時間に依存しうる

通常の共同編集 step では、採否・終了はモデルが action を選び、コードが evidence / confidence / pending / CAS を検証する。  
模擬 HTTP 試験では、**相槌 `respond` だけでは状態は進まない**。試験側が現行 action を返すこと。

一方、明白な称賛・一部の明示終了には **固定経路（モデル非呼出）** が残っている記述もある（`docs/rust-migration-plan.md`、`haiku-player-improvement-plan.md` の C3）。  
ここが揺れていると試験が分裂する。

### 辞書が無いと漢字編集は成立しない

読みをコードが確定できない編集は、保存成功を期待してはいけない。  
失敗時に「なぜ止まったか」が試験・ログ・プレイヤー向けのどれかで追えることを、辞書なしケースの完了条件にする。

## 文書で先に揃えること

試験修正の前に、次の食い違いを一文で決める。

| 論点 | 確認すること |
|---|---|
| 明白な称賛（「いい句だね」等） | pending **なし** → 固定経路で即 close か／常に agent か |
| pending **あり** の称賛・「終了」 | 即 close 禁止で採否確認（`ask`）か |
| 「それにして」 | モデル呼出あり（現行 agent）か、保持中候補のモデルなし確定か |
| プレイヤー明示編集（「上五を『さくらいろ』にして」） | 即保存か、pending 経由か |

`check_workshop_edits.py` 内には、pending ありで「終了」「いい句だね」→ `ask` を期待する箇所と、`check_workshop_combat.py` の即 `closed` 期待が並存しうる。  
**どちらが現行正か**を文書で先に固定してから試験を直す。

残したい旧記述例（要更新または「条件付き」へ）:

- 「明白な称賛は即終了」だけが独り歩きしている箇所  
- 相談案の「それにして＝モデルなし確定」前提の docstring／計画書の古い行

正本候補: `docs/haiku-player-improvement-plan.md`（C2/C3・agent action 表）、`docs/haiku-architecture.md`、`docs/rust-migration-plan.md` の称賛固定経路メモ。

## 推奨作業順

1. **方針の一文**（上表の4論点）を計画書に追記／訂正する  
2. 辞書あり／なしの試験フィクスチャ方針を決める（漢字編集）  
3. 模擬 `install(control, ...)` を action 単位で現行に合わせる  
4. 受理と完了の wait を分ける（combat close、haiku 終了）  
5. vocalization の「却下」を pending 生成経路に付け替える  
6. 最後に該当 `check_*.py` を通し、旧コメント・旧 docs を消す  

Codex へ渡すときは「期待を緩めろ」ではなく、次を禁止付きで渡す。

```text
試験の期待値だけを下げて通すな。
現行の採用・終了・明示編集・pending 規則に合わせて、
模擬モデル返答・完了待ち・辞書条件・docs を同じ変更で揃えよ。
新しい互換ラッパーや「どっちでもよい」分岐を本番コードに足すな。
```

---

## 完了の定義

- 上記5試験が、現行方針を文書化した前提で意図どおり通る（または辞書なし等の意図的スキップが明示される）  
- 「受理直後＝完了」の断言が残っていない  
- 称賛／終了／それにして／明示編集の規則が docs と試験コメントで一致している  
- 漢字編集は辞書あり成功と辞書なし失敗が両方説明できる
