# P1 詳細計画: workshop の契約エラー後に操作修復の意思を保つ

**2026-10-28の後継方針:** 本文の川柳WSに関する原文evidence・confidence・語形・音数・材料条件による拒否、原文からの直接編集、旧 `workshop_validation` の記述は当時の記録。現行はBERT・LLMの解釈を `workshop_response` で受け取り、対象・現在句・版・取消・保存整合性を扱う。[モデル出力の受信と適用](rust-workshop-validation.md)を正とし、旧検査を復元しない。実ログ・試験結果は当時の条件のまま保持し、今回の変更の確認済みへ読み替えない。自動発句・assist・戦闘の契約はこの更新の対象外。

> 当時のレビュー・検討記録です。現行の実装方針は [AGENTS.md](../AGENTS.md) と各機能の最新仕様を参照してください。

**初稿**: 2026-10-06 / Grok 4.5 (xAI)  
**改訂**: 2026-10-07 / Codex（ユーザー指定文面、コードでの補正優先、必要時だけの内部再試行を反映）  
**親計画**: [workshop 終了時の checks 補完計画](2026-10-06-Grok4.5-workshop-close-checks-plan.md)  
**状態**: 採用しない（2026-10-07）。親計画 P0 のコード補完を維持し、単独の終了が成立しなければ再試行せず元の返答本文を使う。本文がなければ無言にする。終了の不合格理由をモデルやプレイヤーへ返さない。以下は過去の検討案として残す。  
**対象**: 既存の再試行プロンプトと、その組み立て・動作の回帰試験。P0 の変更とは分ける。

## 1. 目的と到達点

終了・編集・採否について、モデルが選んだ操作の形式を直せばよい場面で、再試行の指示が普通の会話への変更を促してしまう問題を直す。

- P0 は `inactive` に `checks: []` を補い、checks の欠落だけで正当な終了が止まる経路を除く。
- P1 は、残る契約エラーの再試行で「操作を修復する場合」と「操作を止めて相談へ戻す場合」の指示を整える。
- 操作の許可、原文 evidence、confidence、pending、CAS、保存、戦闘中断の判断は変更しない。
- モデルの `respond` をコードで `close_workshop` に変換しない。締めの台詞を語句で検査して自動終了・棄却する処理も追加しない。

P1 が保証するのは、経路に適した指示を送り、再提出にも既存の検証を通すこと。プロンプトだけで「実モデルが必ず close を選ぶ」とは保証しない。実モデルの改善は別途観測して報告する。

### 1.1 AI の出力不備は裏側で修復する

プレイヤーが「相談はここで終わり」と明確に伝えているのに、AI が必須項目を省略した、型を間違えた、evidence を正しく抜き出せなかった、という理由でプレイヤーに言い直し・再確認・形式修正を求めない。まず、意味を変えず一意に補える不備は既存のコード側の補完で直し、再検証する。それで解決しない場合だけ、同じプレイヤー入力と文脈を保持して、既存の残り一回の内部再試行へ返す。

ここでいう再実行は、棄却されたモデル出力の再生成・再検証と、合格後の操作実行である。まだ実行していない close を一度実行し、実行済みの保存・採用などを繰り返さない。途中の不合格案、JSON の修正説明、不要な聞き返しをプレイヤーに読み上げない。

「モデルの出力に evidence がない」ことと「今回の発話に本人の意思がない」ことを混同しない。確認が必要なのは、原文と直近の文脈を読み直しても、未採用案を採用するか破棄するかなど、本人の選択が本当に未確定な場合。否定・引用・疑問であれば、勝手に操作せず、その発話に応じる。常に聞き返す必要はない。

内部再試行も成立しなかった場合は、成功を装わず、既存の失敗応答で処理できなかったことを短く伝える。AI の形式不備を直すために「もう一度同じことを言って」と要求しない。再試行枠は今回増やさず、無制限の再生成も行わない。

### 1.2 コードで直せるものを、モデルに直させない

処理の順序を次で統一する。

1. **既存の既定値・契約から一意に決まる補正をコードで行う。** 今回は P0 の `checks` 欠落 → `[]` が該当する。モデルへの再問い合わせを挟まない。
2. **補正した出力を通常どおり検証し、合格なら操作を実行する。** 補完は終了許可の代用ではなく、原文意思・confidence・pending・CAS 等の既存検証を維持する。
3. **意味や必要な値をコードで確定できない不備だけ、モデルへ戻す。** 元の出力と検証理由を示し、必要な場合は既存の契約に基づく正しい型・制約も示す。本人の原文を読み直して修復するための、既存の一回の内部再試行を使う。

「正しい型を知っているコードが、必ずモデルへ説明して直させる」という段取りにはしない。モデルに渡す修正例をコードで一意に確定できる場合は、まずその値を自分で補えるかを確認する。元の出力を変えた場合も、検証を省いて実行しない。

今回のコード側の補完は親計画 P0 の範囲とし、P1 に汎用の型変換器、エラー説明用の新しい応答 schema、二重の契約定義を追加しない。明示された不正値を消して通さないという親計画の条件は維持する。原文にない evidence や、採用・破棄の意思、閾値を満たすためだけの confidence は補完対象にしない。

## 2. 現行コードで確認した経路

対象コードは `dogido-rust/src/` 以下。行番号は変わるため、実装時は記載した分岐・関数で確認する。

| 経路 | 現行の入口 | 再試行時の扱い | P1 の扱い |
|---|---|---|---|
| A: 契約エラー | `dialogue/workshop_runtime.rs` の `contract_errors` 非空分岐 | `retry={errors,payload}` を作り、既存の残り一回へ進む | 許可中の操作を修復する短い指示を追加 |
| B: 操作不成立等 | `prepare_conversation_retry` | allowed を会話・検査へ絞り、終了・採否に進まないよう案内 | 分岐条件・allowed・instruction を維持 |
| C: JSON 不成立・途中切れ | `invalid_json` / `output_truncated` 分岐 | 有効な直前 action を確定できず、既存の JSON 再提出へ進む | 独自の操作維持指示を追加しない |
| D: 相談中候補の evidence 修正 | A 内の candidate＋`evidence:` エラー、および `ungrounded_evidence` 特例 | 今回の原文 evidence と保持された候補を使う指示 | 既存の専用指示を優先し、上書きしない |

### 2.1 retry テンプレートは全経路で共有される

`workshop_prompt/mod.rs::prepare_with_assets` は、retry があるとき、その種類を問わず `templates.json` の `retry` を一件の user メッセージに展開する。

したがって、共通テンプレートを無条件の「同じ操作を出し直せ」に変更すると B・C・D にも届く。共通文面を中立にし、A の操作修復指示は既存の `retry.instruction` に置く。

### 2.2 contract_errors の全件が単なる形式不足ではない

`workshop_validation/contract.rs::errors` には、型・必須キーの検査に加え、`action:not_allowed`、`evidence:not_exact`、`evidence:not_in_original` などもある。

A に入っただけで「前の操作の意思・根拠は正しい」と扱わない。元の action が既知かつ現在も許可されている場合だけ修復対象として案内し、原文にない根拠の補作や、操作を通すための confidence の水増しを促さない。一方、evidence の不備だけでプレイヤーの説明不足とも扱わず、元の原文からの抽出を内部でやり直す。再回答の実行可否は従来の検証が決める。

### 2.3 inspect は A に入らない

`workshop_validation/mod.rs` は `inactive` のマージより前に、`inspect` を `conversation::validate` へ渡す。checks の欠落・空配列は `inspection_check_required`、不正な値は `invalid_checks` 等となり、`contract_errors` は空のまま返る。

そのため「A の分岐で inspect 用 instruction を追加する」という初稿の案は採用しない。inspect の再試行方針は今回変更せず、既存の拒否と相談への差し戻しを回帰試験で維持する。

## 3. 採用する実装案

**共通 retry 文面の中立化＋A に限った既存 instruction の利用**に一本化する。テンプレートの二重化、新規 wrapper、新しい分類器、再試行回数の追加は行わない。

### 3.1 共通 retry テンプレート

`workshop_prompt/templates.json` の `retry` を次の趣旨へ変更する。`retry` スロットは維持する。

```text
さっきの一手について、コード側から返ってきた結果と、次の返答に必要な指示を下に示すで。
{{retry}}
instruction があるときは、今回許可されとる action と一緒にちゃんと読んで従ってな。
前の一手がほんまに実行されたかどうかを、自分のセリフだけで判断したらあかんで。ちゃんとコードの結果を見てな。
今回の認識原文にない操作の根拠を勝手にでっち上げんと、指定された JSON だけを返してな。
```

全失敗を「形式不足」と呼ばず、全失敗に「相談を続けよ」「同じ操作を維持せよ」のどちらも一律には課さない。

### 3.2 A の操作修復 instruction

`contract_errors` 分岐で作る `retry` オブジェクトを利用する。追加する条件は以下に限定する。

1. payload の action が、既存の操作 action のいずれかであること。対象は `close_workshop`、`accept_pending`、`reject_pending`、`stage_player_edit`、`stage_conversation_candidate`、`propose_revision`。
2. その action が当該試行の allowed に含まれていること。
3. 既存の candidate evidence 専用 instruction が必要な場合は、それを優先すること。汎用の操作維持指示と矛盾する二文を重ねない。

これらは再提出の案内を選ぶ条件であり、操作を実行する新しい許可条件ではない。元の payload、errors、現在句・pending・候補・原文は保持する。

close の文面（ユーザー指定）:

```text
さっき選んだ一手は close_workshop やで。フォーマットや入力の修正で通る終了なら、出されたエラーを直してもう一度 close_workshop を出し直してな。
終了のセリフだけを respond や explain に移して、終わった気になって誤魔化したらあかんで。
evidence は今回の認識原文からそのまま抜き出して、原文にない根拠をでっち上げたり、エラーを通すためだけに confidence の数値を水増ししたりせんといてな。
もし必要な根拠が発話の中にないなら、終了を無理やり押し通さんと、今回許可された会話の一手（ask など）で確認や説明をしてな。
```

最後の「必要な根拠が発話の中にない」は、原文・文脈を読み直しても本人の意思や必要な選択が見つからない場合を指す。AI が一度抽出に失敗しただけでは該当しない。形式や抽出の修復はプレイヤーへ見せず、内部で完了させる（§1.1）。

他の対象操作も、既存の action 名と役割に合わせた同趣旨の短い指示にする。action 名は既知の値だけを使い、不正・未許可 action を「維持すべき操作」として案内しない。

既存の candidate evidence 指示は、`stage_player_edit` から `stage_conversation_candidate` への適切な対応を案内することがある。ここで同じ action を強制しない。意味上の対象・本人の意思を保つことと、すべての再試行で文字列として同じ action を固定することを区別する。

### 3.3 B・C・D の維持

- `prepare_conversation_retry` の呼び出し条件、allowed の絞り込み、instruction は変更しない。
- JSON 不成立・途中切れから、直前 action を推定して操作修復を強制しない。
- candidate evidence の既存二箇所の指示を維持する。今回の evidence を過去発言で代用しない。
- inspect・会話系・followup 専用経路を、A へ移さない。
- 再提出後も同じ validator と実行前検証を通す。再試行枠は既存の `0..2` のまま。

### 3.4 CONVERSATION_PROTOCOL との整合

`dialogue/workshop_runtime.rs` 冒頭の `CONVERSATION_PROTOCOL` は、retry メッセージより後に追加される。現行の次の一文を条件付きにする。

```text
実行できない理由が返ってきたら同じ対象について説明・相談を続ける。
```

置換案:

```text
再試行では、その回の instruction と許可 action に従ってな。
AI 側の出力形式や項目、evidence の抜き出しに不備があっただけなら、今回の原文と文脈を読み直して、裏側の再試行で直してな。プレイヤーに同じ依頼を言い直させたり、もう分かっとる意思を確認し直したりせんといてな。
操作を止める指示があるときは、その制限を守ってな。その場合も、自分の出力不備をプレイヤーの説明不足に置き換えたらあかんで。
プレイヤーへの確認は、原文と文脈を読んでも本人の意思や必要な選択がほんまに未確定なときだけにしてな。終了していないのに、終了したとは言わんといてな。
```

「まだ行っていない操作を別の action の speech で実行済みとは言わない」という既存指示は維持する。上記以外の人格・編集・採否・終了方針をまとめて書き換えない。

## 4. 回帰試験

### 4.1 プロンプトと組み立て

| ケース | 必須の確認 |
|---|---|
| A: 許可中の close の契約エラー | 元の payload と errors、close 修復 instruction が再提出へ渡る |
| A: 未許可・不明な action | その action を維持する操作修復指示を付けない |
| D: candidate evidence エラー | 既存の原文・保持候補向け instruction が残り、操作名の固定と衝突しない |
| B: 否定・疑問・引用・条件付き終了 | allowed が既存どおり会話系に絞られ、「終了や採否へ進まない」指示が残る |
| C: JSON 不成立・途中切れ | 不明な操作を保持させず、既存の再提出枠で処理する |
| inspect の checks 欠落・空・不正値 | 既存の拒否・差し戻し。A 専用の操作修復指示を付けない |
| 共通テンプレート | A/B/C/D のどれにも、無条件の操作強行・会話化を指示しない |
| 最終プロンプト | 後から追加される `CONVERSATION_PROTOCOL` が retry.instruction と矛盾しない |
| AI 側の形式・抽出不備 | 同じ原文で内部再試行し、プレイヤーに言い直しや不要な終了確認を求める指示を出さない |
| 実際に選択が未確定 | pending の採用・破棄など、本人の選択が必要な確認を妨げない |

`workshop_prompt::prepare` 単体では retry があると messages は従来どおり三件。runtime ではその後の追加メッセージも含めて検査し、最終 messages 全体を三件と誤認しない。既存のサイズ上限、editable defaults、補助 instruction の扱いを維持する。

### 4.2 模擬 HTTP の必須試験

既存の `check_workshop_runtime.py` と fixture を利用する。新しい試験サーバーや判断経路は作らない。

**A の正常な修復:**

1. pending のない open の workshop に、本人の明確な終了入力を送る。
2. 一回目は、正当な `close_workshop` と原文 evidence に、意図的な `checks: "meter"`（配列でない）を添えた模擬応答を返す。
3. 二回目のリクエストで同じ原文、エラー、close 修復 instruction を確認する。二回目を待っている間、一回目の不合格案や聞き返しが当該 turn の音声・表示・再生済み会話へ出ていないことを確認する。
4. プレイヤー入力を追加せず、二回目に正当な `checks: []` の close を返す。
5. `workshop_action == close_workshop`、内部状態と HUD が `closed`、処理・模擬再生完了まで確認する。モデル呼び出しは既存の二回以内。終了処理は一度だけ実行される。

同じ原文内に終了意思があるのに、初回モデルの evidence だけが不一致というケースも確認する。原文を変更・再入力させず、二回目で正しく抽出した evidence を再検証して閉じる。一方、二回目も不正な場合は閉じず、既存の失敗応答と状態を確認する。明確な終了意思・pending なしのこのケースで、AI の修正をプレイヤーへの質問に転嫁しない。

P0 適用後は checks の「欠落」だけでは再試行が発生しない。初回モデル応答をコードが補完し、追加のモデル呼び出しもプレイヤー入力もなく閉じることを親計画 P0/P2 で確認する。P1 の再試行試験は、親計画で自動補完の対象にしない明示的な型不正で起こす。

**壊してはいけない境界:**

- 否定・疑問・引用・条件付きの終了案は、引き続き操作されず open のまま相談へ戻る。
- 原文にない evidence を使った再提出は操作に通らない。instruction の追加を採用権限と扱わない。
- candidate evidence の既存修復と、pending の採用・破棄・終了条件を維持する。
- inspect は checks 欠落・空・不正値を拒否し、正当な項目付きなら従来どおり検査できる。
- 普通の `respond` は action と非空の speech で受け取る。

二回目のモデル応答をモックで close に固定した結果は、runtime の接続検査である。モデルが自力で close を選び直す証拠にはしない。二回目が `respond` の場合も、台詞からコードが終了を推測する仕組みは追加しない。

### 4.3 実モデル・実機確認

同じ終了入力・同じ workshop 条件を用い、実モデルの action、検証結果、最終状態を確認する。実際に再試行が起きた場合は、一回目・二回目を分けて記録する。再試行が起きなかった実行を P1 の改善根拠にはしない。

型不正の初回応答を注入し、二回目だけ実モデルへ渡す試験を行う場合は「初回は人工的に作ったエラー」と明記する。モデルが自然に起こした失敗と混同しない。

ゲームイベント・音声を模擬した試験と、Minecraft・マイク・実音声再生の試験は別に報告する。実機を実施できていない場合は未確認とし、自動試験の成功で置き換えない。

## 5. 実装時の対象ファイルと順序

| 対象 | 変更内容 |
|---|---|
| `dogido-rust/src/workshop_prompt/templates.json` | 共通 retry の中立化 |
| `dogido-rust/src/dialogue/workshop_runtime.rs` | A の既存 instruction 利用、protocol の該当一文 |
| `dogido-rust/src/workshop_prompt/tests.rs` と既存 fixtures | 共通文面・組み立て・既定値の追従 |

実装順:

1. 作業開始時の HEAD と変更状況を確認し、他作業の変更を含めない。
2. P0 が適用済みかを確認し、欠落試験と P1 の型不正による再試行試験を分ける。
3. 共通 retry、A の instruction、protocol の一文を一つの小さな変更として揃える。
4. 該当プロンプト fixture と既存試験の期待値を、今回の文面変更に限って更新する。テストを削除・一括無効化して通さない。旧 Python 本体や比較 oracle を復活させて再生成しない。
