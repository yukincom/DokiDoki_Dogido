## 1. この文書の位置づけ

この文書は、将来追加する可能性がある次の機能をまとめた構想メモである。

- プレイヤーの操作を補助する支援アクション
- 洞窟や別ディメンションからの救助
- 所有する乗り物の呼び戻し
- 保存した川柳とプレイ記録を見る「マイクラ句集UI」
- カタログ JSON を読み物として閲覧する「ドギドのあんちょこ」
- App Intents / Shortcuts 等を使った OS 連携

いずれも未実装であり、現行の実装優先度を置き換えない。

当面は [相棒としての完成度ガイド](companion-maturity.md) に従い、観測の解像度、対話品質、川柳ワークショップを優先する。ここに挙げる機能は、既存の判断・安全・記憶基盤が安定してから、小さな単位で検証する。

## 2. 共通方針

### 2.1 冒険を代行しない

ドギドは、プレイヤーの代わりに探索や戦闘を行う bot ではない。

支援アクションは、次のような「困った」を減らす目的に限定する。

- 必要な道具へすぐ持ち替えたい
- 洞窟や別ディメンションから帰れない
- 所有している馬などを見失った

自由なテレポートや自動攻略ではなく、初めてサバイバルモードを遊ぶプレイヤーが冒険を続けやすくする補助機能として設計する。

### 2.2 明示入力はコード、曖昧な意図だけを LLM で抽出する

「剣」「脱出して」のような明示入力は `player_input` の決定論的な規則で先に処理する。救助のように自然な言い回しが多く、規則だけでは分類できない場合に限り、LLM を閉じた型の意図抽出へ使う。LLM の結果はアクション候補であり、実行の許可ではない。

- 明示入力の正規化と意図フラグ: `player_input` 側
- 規則で確定しない「怖い」「もう無理」「帰りたい」などから、閉じた救助意図を抽出: LLM（任意経路）
- 確認文の選択と、肯定・中止の判定: 状態機械 / policy（発話文はカタログを基本とし、LLM を使う場合も言い回しだけに限定する）
- 現在の状態と発動条件の判定: 状態機械 / policy
- 座標、所有権、対象、安全地点の検証: 決定論的なコード
- 許可されたアクションの実行: コードから Minecraft adapter を呼び出す

LLM を使う場合は「救助を求めていそうか」「外へ出たいのか、拠点へ帰りたいのか」を閉じた enum へ抽出する。ただし、LLM の出力を直接ゲームコマンドへ変換しない。判定結果を許可された型付きアクション候補へ正規化し、プレイヤーの確認とコード側の安全検証を経てから実行する。

これは、LLM を主に言い回しと閉じた抽出へ使う現行方針を、支援専用の限定 enum へ拡張する将来案である。実装する際は、状態機械・player input・LLM route の正本も合わせて更新する。

### 2.3 実装順は小さく保つ

最初に実装する場合は、影響範囲の小さい持ち替え機能から始める。

```text
音声入力
  -> player_input の決定論的 routing
  -> 規則で確定しない場合だけ、LLM による閉じた意図抽出
  -> 型付きアクション候補へ正規化
  -> 必要な確認
  -> 状態・入力検証
  -> Minecraft adapter で実行
  -> 成功 / 失敗を記録して返答
```

この経路を固めてから、ワープや召喚のように安全判定が必要な機能へ広げる。

## 3. 支援アクション

### 3.1 剣への持ち替え

敵に狙われている際、音声で「剣」と言うと、プレイヤーのホットバーの手持ちを剣へ切り替える。

ドギド自身が武器を持って戦う機能ではない。武器を使うのはプレイヤーであり、ドギドは持ち替えだけを補助する。

初期スコープは剣に限定する。ブロックの音声切り替えには対応せず、通常の Minecraft と同じくプレイヤーが手動で切り替える。

選択規則:

- 剣が複数ある場合、指定がなければ攻撃力が低い剣を優先し、その中から耐久値が低いものを選ぶ
- 剣がない場合は「剣がない！ これでどうや！？」と返し、トライデント（槍）、斧、弓の順で持ち替える
- 上記の武器もない場合は、クワやツルハシなど、手持ちの中で攻撃力が高い道具を候補にし、耐久値が低いものから選ぶ
- 戦闘中の誤認識と連続実行の抑制
- adapter からホットバー選択を変更できる範囲

### 3.2 脱出・救助・帰還

洞窟、地下、ネザー、エンドなどから帰れなくなる事故を防ぐ機能。

「好きな場所へ移動する」機能ではなく、「冒険から帰れない状態を解消する」機能として扱う。

第一段階はシングルプレイの integrated server を対象とし、LAN 公開は前提にしない。リモートのマルチプレイでは client がサーバー権限を偽装せず、server-side mod または許可済みコマンドなど、接続先サーバーが明示的に認める実行経路がある場合だけ対応する。

#### 発動フロー

1. `player_input` が明示入力を判定し、規則で確定しない場合だけ LLM が閉じた救助意図を抽出する
2. 判定結果を型付きの救助アクション候補へ正規化する（LLM 出力は実行許可にしない）
3. 状態機械が現在地と要求の種類を確認する
4. ドギドが脱出の希望を短く確認する
5. プレイヤーから明確な肯定を受ける
6. コード側で帰還先と安全性を再検証する
7. ワープを実行し、結果をログへ残す

「怖い」という感情表現だけで自動ワープしない。曖昧な場合は「外に戻る？」と確認し、少なくとも一度は明確な肯定を受ける。

#### オーバーワールド

Y 座標だけでは山中洞窟や海底洞窟を判定できない。第一候補として、プレイヤーが最後に滞在した安全な地表地点を記録する。

安全地点は、少なくとも次を満たす場合だけ更新する。

- 空が見える
- 足元が安全
- プレイヤーが収まる空間がある
- 溶岩、落下、粉雪、水没などの即時危険がない
- 条件が数秒間安定している

想定する挙動:

```text
地表を移動
  -> safe surface point を更新
洞窟へ入る
  -> 更新を停止
救助を確定
  -> 最後の safe surface point を再検証して移動
```

「外に出して」と「家に帰りたい」は分ける。

- 外に出して: 最後の安全な地表地点
- 家に帰りたい: 有効な個人リスポーン地点として登録されているベッド

多くの子どもユーザーは X / Z 座標を把握していないと考えられるため、座標を指定して拠点登録することは前提にしない。ワールドスポーンとは異なる有効な個人リスポーン地点が設定されている場合、そのベッドの場所を「家」とみなす。

ベッドが破壊されている場合や個人リスポーン地点が無効な場合に、村などの明確な構造物や明示登録した地点を代替候補にするかは、今後の検討事項とする。

#### ネザー / エンド

- ネザーは最後に安全確認できたポータルを帰還先の第一候補にする
- エンドは可能な限り正規の帰還経路を優先する
- ポータルが破壊・到達不能の場合は、最後に記録された安全なオーバーワールド座標への移動を救済候補とする
- エンドの帰還経路が破壊・到達不能の場合の救済は別途検討する

通常の帰り道を優先し、利用できない場合だけ強い救済へ段階的に切り替える。

### 3.3 所有する乗り物の呼び戻し

馬など、自分の乗り物を見失ったときに呼び戻す機能。

対象は「近くにいる乗り物」ではなく、呼び出したプレイヤーが所有している対象に限定する。

- 飼いならし状態と所有者を確認する
- 名前が付いている場合は指名に利用する
- 名前の指定がない場合の選択規則を設ける
- プレイヤー周囲から、対象の当たり判定が収まる安全地点を探索する
- プレイヤーから 2 マス程度離れ、乗るための空間を含む最低 2 × 2 マス程度の平坦で安全な場所を候補にする
- 壁、崖、水中、溶岩など危険な召喚先を除外する
- 安全な平地がない場合は実行せず、「ここはちょっと狭いんちゃう？ ちと歩いて平らな場所を探してみよか」と移動を促す
- 同一ディメンション内に限定する
- 乗り物に「ドギド」と名付けられている場合の呼び分けは、今後の検討事項とする

別ディメンションをまたぐ呼び戻しは、Minecraft の移動ルールを大きく変えるため対象外とする。

## 4. 川柳データとマイクラ句集UI

### 4.1 目的

保存した川柳を一覧表示するだけでなく、川柳が詠まれたときの景色、作者、場所、日時を一緒に残し、Minecraft の冒険記録として見返せるようにする。

既存の [川柳・Senryu ロードマップ](senryu-roadmap.md) にある「保存した川柳を見る UI」を拡張する案として扱う。

### 4.2 データの分離

「川柳そのもの」と「一度詠まれた出来事」は分けて保存する。

#### 川柳エントリ

既存の `haiku_entries.jsonl` と `GET /api/v1/memory/haiku` を基礎にする。

主な情報:

- 句の本文と読み
- 作者（ドギド / プレイヤー）
- 作成日時
- バイオームや状況
- interpretation
- revision / critique との参照

#### 表示用アセット / 詠唱記録

スクリーンショットを追加する場合は、既存エントリを置き換えず、別の記録または参照として紐づける。

- 対応する川柳エントリ ID
- 撮影日時
- world / dimension / biome
- プレイヤー込みの画像
- プレイヤー視点の画像
- 表示に必要な補助情報

保存形式を拡張する際は、既存 JSONL の互換性と [記憶アーキテクチャ](memory-architecture.md) の境界を維持する。

### 4.3 スクリーンショット

川柳が詠まれたとき、次の 2 枚を保存する案がある。

1. プレイヤー込みの記念写真
2. プレイヤー視点で景色を中心にした写真

撮影方向はその時点のプレイヤー設定を使う。

完成画像だけを保存せず、元画像と川柳テキストを分ける。マイクラ句集UI側で本文、作者名、日時などを重ねることで、縦書き・横書き、フォント、位置を後から変更できるようにする。

### 4.4 マイクラ句集UI

初期候補:

- 一覧: 日付、作者、バイオーム、元句 / 直し句
- フィルタ: 期間、biome group、作者
- 詳細: 川柳、スクリーンショット、interpretation、revision
- 表示: プレイヤー込み / 景色のみの切り替え
- 任意: お気に入り、Markdown / 画像エクスポート

将来候補:

- 月ごとの冒険記録
- 同じ一句に紐づく複数の景色
- 川柳とスクリーンショットのスライドショー

最初からクラウド同期やソーシャル投稿を必須にしない。

## 5. ドギドのあんちょこ

### 5.1 目的

「ドギドのあんちょこ」は、ドギドが Minecraft の世界を理解し、会話や川柳に利用しているカタログ JSON を、人間が読み物として閲覧するための UI である。

一般的な攻略 Wiki の代替ではない。Mob、バイオーム、ブロック、アイテム、構造物などについて、既存カタログに収録されている説明や観察を、昔の攻略本に近い読み物として見せる。

既存データと読み込み処理を利用し、最初は閲覧専用のローカル Web UI として実装する。

あんちょこは、発句が参照するものと同じ保存済みカタログ JSON と既存ローダーを読む。発句時に `note` を句点単位へ分ける `source atom` は実行時の派生物であり、第二のカタログ正本にはしない。句の前に実際に話した見どころも `preface_interpretation` atom として利用できるが、カタログ事実とは別 provenance であり、あんちょこの原文へ混ぜない。元の説明文は変更せず、UI では原文と既存オーバーレイを合成して表示する。

### 5.2 最小 UI

- トップ: Mob、バイオーム、ブロック、アイテム、構造物などのカテゴリ
- 一覧: 名前と短い説明
- 詳細: カタログに含まれる解説、特徴、読み、川柳用の情報
- 検索: 名前、読み、説明文を対象にした全文検索
- 任意: 元の JSON を確認する表示

カタログごとに JSON の構造が異なるため、名前、読み、説明などの共通項目だけを揃え、それ以外はカテゴリ別の詳細表示にする。

### 5.3 プレイヤーとの会話から増えるメモ

川柳を一緒に直す過程で判明した読み方や注意点を、対応するカタログ項目へ重ねて表示する。

詳細画面では、次のように情報源を分ける。

- 基本情報: リポジトリに含まれる元のカタログ JSON
- 読みと共通補足: `catalog_corrections.jsonl` 等に保存された訂正
- ドギドのメモ: critique / lesson から得たプレイヤー固有の注意点
- 関連する句: 注意点が生まれた `haiku_entries` / revision
- 記録日: その会話や訂正が保存された日時

プレイヤーとの会話から得た情報は、元のカタログ JSON へ直接書き込まない。共通カタログ、訂正オーバーレイ、プレイヤーごとの記憶を分離し、UI で合成する。

```text
元のカタログ JSON
  + 読み訂正・共通の補足
  + プレイヤーとの会話から生まれたメモ
  = ドギドのあんちょこ
```

個人メモをカタログ項目へ紐づける場合は、少なくとも次の情報を保存する。

```json
{
  "catalog_type": "biome",
  "catalog_id": "plains",
  "note_type": "reading",
  "note": "「草地」は「くさち」と読む",
  "haiku_entry_id": "...",
  "created_at": "..."
}
```

公開版の「あんちょこ」は共通カタログのみを表示し、ローカル版ではそのプレイヤーとの訂正や関連する句も表示できる構成にする。会話ログ全文をそのまま表示するのではなく、保存された構造化メモと関連する句への参照を使う。

## 6. OS 連携

App Intents、Shortcuts、Siri などを、マイクラ句集UIやドギドのあんちょこのデータと操作を OS から見つける入口として利用できる可能性がある。

想定例:

- 「今日ドギドが詠んだ川柳を開く」
- 「現実の季節にあったバイオームの川柳を探す」
- 「この前のスクリーンショットを見る」
- 川柳のスライドショーを開始する
- Minecraft のサウンドトラックを再生する際、BGM と川柳データのバイオームを対応づけ、再生中に関連する句を表示する

ただし、OS AI を共有データ層の代わりにはしない。Minecraft 側と各 UI は、通常の API または共有ストレージを通じて同じデータを見る。OS 連携が利用できない環境でも基本機能が動く構成にする。

次の点は実装前に、対象 OS と SDK の公式仕様で確認する。

- App Entity / App Intent で公開できるデータと画像の制約
- Intent から特定の川柳画面を開く方法
- 複数アプリの操作を一つの要求から実行できる範囲
- Shortcuts を明示的な実行手順として用意する必要があるか
- OS 連携を使わない場合の URL scheme / ローカル API 等の代替

## 7. 安全設計

支援アクションは、共通の安全基盤を通す。

- LLM の文章をゲームコマンドとして直接実行しない
- 許可されたアクションだけを型付き入力として受け取る
- 状態、対象、所有権、ディメンションを実行直前に再確認する
- ワープや召喚は、必要に応じて明示確認を挟む
- 安全地点が見つからない場合は実行しない
- 成功、失敗、中止と理由を記録する

ワープでは追加で次を確認する。

- 移動先チャンクを安全に読み込めるか
- 足元と頭上に十分な空間があるか
- 窒息、落下、炎上、水没の危険がないか
- 記録地点が変化している場合に代替地点を探索できるか

子ども向けの確認文は短くし、中止や「まだ大丈夫」を確実に尊重する。

## 8. 調査・実装の順序

### 先に調べる

- Fabric client mod からホットバー選択を変更する方法
- 所有する馬、名前、直近の騎乗を取得する方法
- プレイヤーと Mob の安全地点探索
- チャンク未読込時のワープ / 呼び戻し
- 安全地点、拠点、ポータルのワールド単位の永続化
- スクリーンショット 2 枚の撮影方法と保存タイミング
- 既存 JSONL と API を壊さない画像参照の持ち方
- カタログ閲覧用 API とカテゴリごとの表示スキーマ
- critique / lesson とカタログ項目を紐づける ID の保存方法
- 公開カタログとプレイヤー固有メモのデータ境界
- 対象 OS の App Intents / Shortcuts の制約

### 実装する場合の順序

1. 剣への持ち替え
2. アクションの入力検証、確認、実行ログ
3. safe surface point の記録
4. オーバーワールドの救助
5. 同一ディメンション内の乗り物呼び戻し
6. 川柳へのスクリーンショット参照追加
7. 最小のマイクラ句集UI
8. ドギドのあんちょこ（共通カタログの閲覧）
9. あんちょこへの読み訂正・プレイヤーメモ表示
10. OS 連携

各段階は独立して動作確認できる単位に分け、現行の状態機械、対話、記憶方針を変更する場合は、それぞれの正本ドキュメントも合わせて更新する。
