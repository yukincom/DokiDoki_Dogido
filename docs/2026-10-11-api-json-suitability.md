# API / JSONの適性見極め（2026-10-11）

今回の採用は、**自動川柳はJSON、所有馬の呼び戻しはnative tool API**。同じGemma 4 26B QATでも、創作と対象選択で成績が分かれた。APIが常に軽量という結果ではない。

## 実測に基づく選択

| 用途 | 採用・扱い | 実測の根拠 |
|---|---|---|
| 三行の自動川柳を作り、出典・音数を検査する | JSONを継続 | QAT比較はJSON 9/9採用・中央値4.033秒、API 6/9・6.188秒。厳密5/7/5はJSON 9/9、API 3/6 |
| 依頼を受け、現在一覧から呼び寄せる一頭を選ぶ | native tool API | 最終105試行はAPI 102/105、JSON 96/105。実行すべき36試行の正しい個体選択はAPI 36/36、JSON 27/36 |
| workshopの明示的な局所編集・辞書検査 | 既存native toolを維持。優劣比較は未確定 | E4Bの接続・原文・CAS検査を確認済み。ただし同条件JSONとの直接比較ではない |
| 普通の雑談・言い回し | 既存の会話契約を維持 | 今回は呼び寄せcapabilityがある通常会話に限定して候補要求を追加。雑談全般の形式変更を推奨する比較ではない |
| 状態変更・採否・保存・世界操作の実行 | Rust/Fabricの検証で確定 | APIでも誤った候補選択は起きる。モデルの出力形式だけを実行権限にしない |

川柳の詳細は [QAT比較](2026-10-11-gemma26b-qat-comparison.md)、workshopは [native編集接続](2026-10-10-workshop-edit-tool.md) を参照。川柳のAPI不採用3件は後段の根拠照合の外形不成立で、native候補提出そのものは12/12回受理されている。用途と検査のどこで差が出たかを分けて読む。

## 馬の最終比較

依頼判定の一回目には所有馬一覧を渡さず、本人の依頼を受理した後だけ二回目で一覧を渡す。両方式で同じ候補・人格・意味指示・原文検証・個体検証・最大二回を使った。JSONは本文のaction、APIはlist_horses / select_horseのnative tool callで受け取る。APIの通常返事は本文テキストのため、外形指示は方式に合わせて異なる。

| 最終35ケース × seed 3個 | JSON | API |
|---|---:|---:|
| 期待どおりの完遂 | 96/105 | **102/105** |
| 呼ぶべき個体の正しい選択 | 27/36 | **36/36** |
| 呼ばない場面で有効な会話応答 | 69/69 | 66/69 |
| 検証後の誤実行 / 別個体実行 | 0 / 0 | 0 / 0 |
| 検証器で棄却した選択 | 0 | 3 |
| 全試行のLLM所要時間中央値 | 2.138秒 | 2.225秒 |
| 呼ぶべき試行の中央値 | 2.322秒 | 2.488秒 |
| p95 | 2.398秒 | 2.573秒 |
| LLM呼出し数 | 165 | 165 |
| 入力token合計 | 185,283 | 198,918 |
| 出力token合計 | 4,485 | 4,380 |

JSONの9失敗は、一頭しかいない無名馬・文脈で示した馬・「うちの子」への不要な聞き返し（各3回）。APIの3失敗は騎乗者のいる馬の選択で、Rustがeligibleを再検査して移動前に全件棄却した。正しい拒否文を返せた試行とは数えない。

誤実行と別個体選択を先に見て、その条件を満たす中で対象選択の成績を優先し、APIを採用した。JSONの方が呼び寄せ時に約0.17秒速く、入力も少ない。速度差を理由にAPI採用とはしていない。APIの呼出しは実移動そのものではなく、コードへ依頼・選択を渡すための契約である。

## 条件と試行の分離

- モデル: `lmstudio-community/gemma-4-26B-A4B-it-QAT-MLX-4bit`。既存8080のlistener PID・起動引数・応答で確認。サービス・モデルは再起動していない。
- MLX-LM 0.31.3。Thinking off、temperature 0.65、一回192 token、seed 101/202/303。方式の順序を交互にし、事前実行各一回を除外した。seed指定の非batch経路。cacheを消さず、共有モデルを使用。
- 非操作試行の成功条件は有効かつ非空の会話応答。会話の自然さや観測との整合を全件人手評価した数値ではない。
- 測定時間はHTTPリクエストから応答までの合計。オフラインprobe起動時間・ゲーム配送・足場探索・音声・出現演出を含めない。
- 最終コーパスは新しい名前・表現35例。先行ケースの意図分類を引き継いだパラフレーズ評価であり、独立した外部評価ではない。seed違いでも同じ選択が多く、105個の独立な状況を意味しない。

先行試行も保持した。初期の一段階版はJSON 84/90（誤実行6）、API 63/90（誤実行9）で採用しなかった。二段階の初版35例ではJSON 93/105、API 96/105で誤実行は両方0。その結果を開発材料にし、両方式へ同じ候補の読み方・原文の扱いを補足した後、別表現35例の最終比較を行った。初版の点数を最終版の未使用評価に混ぜない。

## 再現と保存

比較時点の両実装、corpus、manifest、全リクエスト・応答・usage・判定はローカルGitの比較保存commitに置く。採用後の作業ツリーにはAPI実装だけを置き、JSON操作の変換・設定切替・失敗時fallbackは残さない。通信としてのJSONシリアライズと、モデル本文JSON方式は別の意味である。

候補要求と選択のprompt、厳密decoder、validatorは実モデルprobeと本体で共有する。採用後は `check_horse_recall_model.py` で同じAPI境界を再検証できる。動作の範囲と自動検証は [所有馬の呼び戻し](2026-10-11-horse-recall.md) を参照。

Google公式の [function calling説明](https://ai.google.dev/gemma/docs/capabilities/text/function-calling-gemma4) と [Gemma 4の会話形式](https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4) はnative呼出しの利用方法を示す。JSONより速いという保証ではなく、今回の用途別実測を採用根拠とする。
