## 1. Python と Rust で「返し方の契約」が違う

反応 leaf（`death` / `ambient` / `deep_dark_ominous_sound` など）について:

| | Python | Rust（本番寄り） |
|---|---|---|
| 入口 | `build_reaction_messages(..., choose_silence=False)`（既定） | `companion_prompt::dialogue(mode)` |
| 契約 | `speech_contract`（素のセリフだけ） | `choice_contract`（JSON speak/silent） |
| 後処理 | `clean_output` + usable/style | `speech_choice::parse` |

同じ `reaction_situations.json` を読んでいるのに、モデルへの「どう返せ」がパスで分かれている。  
そのため同じ観測でも、片方は素の日本語、片方は JSON、片方はフェンス付き JSON、のようにぶれやすい。

`tests/test_dialogue_character_mode.py` も `choose_silence=True`（Rust 相当）と `False`（Python）を明示的に分けて比較している。意図的な互換分岐ではあるが、出力トラブルの切り分けコストが高い。

レビュー時の実測（`build_messages`）:

- `deep_dark_ominous_sound` / `ambient` / `aftermath` / `player_chat` → Python 経路はいずれも `speech_contract`
- `build_reaction_messages(..., choose_silence=True)` だけが \`\`\`json を含む `choice_contract`

---

## 2. フェンス除去が haiku だけにある

Rust でコードフェンス（\`\`\`）を剥がす処理は、現状 **`dogido-rust/src/haiku_response.rs` の `strip_code_fence` のみ**。

反応・通常対話の共通パーサ `speech_choice::parse`（`dogido-rust/src/speech_choice.rs`）は:

```rust
serde_json::from_str(raw.trim())
```

のみ。先頭が \`\`\` の返答は即 `invalid_contract` → 固定 fallback。

呼び出し側:

- `reaction_leaf.rs` → `speech_choice::parse`
- `environment/reaction.rs` → 同上
- `chat_validation.rs`（`choice_enabled` 時）→ 同上

**反応以外の通常チャットでも同じ穴**がある。haiku だけ耐性がある非対称。

---

## 3. Python の `clean_output` がフェンス JSON を壊す

`dogido_server/llm/sanitize.py` の `clean_output` は行分割ベース。  
フェンス付き speak JSON を食わせると、本文ではなく **\`\`\` だけ** が残ることがある。

レビュー時の実測:

| 生出力 | `clean_output` | `is_usable_output` |
|---|---|---|
| \`\`\`json + speak JSON + \`\`\` | \`\`\` | False → fallback |
| 素の speak JSON | JSON 文字列のまま | False → fallback |
| 素の日本語セリフ | そのまま | True |

最終セリフに \`\`\` が残ることは通常少ない（usable で落とす）が、ログ上は「壊れた出力」に見え、原因切り分けを誤らせやすい。

---

## 4. prompt_lab では直ってて、本番だけ古い

`dev_tools/prompt_lab/candidates/*.json` の `choice_contract` からは、\`\`\`json 例示がすでに消えている。

本番正本 `dogido_server/llm/companion_prompts.json` だけが、禁止例としてリテラル \`\`\`json を残している。

結果として:

- ラボ: きれいに見える／フェンスが出にくい
- 本番・fixture: コードブロック臭い／フェンス誘発しやすい

という食い違いが起きやすい。詳細は親レビュー `2026-10-03-Grok4.5-CodeReview.md` の P0。

---

## 5. fixture に \`\`\`json が大量コピーされている

`dogido-rust/src/reaction_leaf/fixtures.json` には、system 文言経由で \`\`\`json が多数埋まっている（親レビュー時点のカウント: 332）。

Markdown や一部ビューアで開くと、`choice_contract` 内のフェンス開始列からコードブロックが開き、後続の JSON（`situations` / `sculk_sensor` 含む）が枠に飲み込まれる。  
「あの行がおかしい」ように見える表示上の誤認の温床。

本番 `choice_contract` を直したあとは、fixture 再生成で残存をゼロにする必要がある。

## 症状との対応

報告されやすい見え方と、上の歪みの対応:

| 見え方 | 主な寄与 |
|---|---|
| 生ログ／ラボ表示にコードブロック | 4, 5、および本命の \`\`\`json 例示 |
| パース失敗で固定文に落ちる（一言が消える） | 2、場合により 1 |
| Python 互換と Rust 本番で挙動が違う | 1, 3 |
| `situations.sculk_sensor` 行が壊れて見える | 5（表示誤認）。データ定義自体は正常（親レビュー） |

## 修正方針（実装しない。親レビューと対応）

- **P0**: 本番 `choice_contract` からフェンス例示を削除（親レビュー）
- **P1**: `speech_choice::parse`（または finish 直前）でフェンス除去。チャット・反応の両方に効く
- **P2**: Python / Rust の反応契約をどちらに寄せるか明示的に固定
- **P3**: Python leaf の fence strip +（JSON 契約なら）`speech` 抽出
- **P4**: fixture 再生成と、raw / finish 理由 / 確定発言の再現手順固定
