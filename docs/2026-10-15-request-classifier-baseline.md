# 依頼分類器と既存パイプラインの比較（2026-10-15）

## 結論

同じ199件で、正解ラベルと処理先の一致は**既存119/199（59.8%）、ModernBERT-Ja v1.8 / seed44は175/199（87.9%）**だった。差はあるため「既存とほぼ同じなので分類器は不要」とは判断できない。ただし既存側の数値は分岐を観測した代理指標であり、実行・返答の成功率ではない。

**分類器だけを追加しても解決しない後段の課題が大きい。** 剣では既存LLMも依頼と判断したのに原文検証で止まる例、敵では対象・質問属性を取り違える例、呼び戻しでは別の種類や名前の個体を選ぶ例があった。分類器は種・個体・質問属性を出さないため、ラベルの改善をそのまま操作成功率の改善とは見なさない。今回の作業は比較と記録までとし、本体には分類器を接続していない。

## 比較条件

- 分類器担当の既存予測ファイルから、test 75件・regression 40件・long 24件・moving 60件を原文と履歴のまま使用。分類器側は保存済み予測を利用し、再学習・再推論・gold修正は行っていない。
- 既存側は正本HEAD `9b0b1187dbdd9e9a5e923ebc89143f96b5e89dea` と当時の未コミット変更を含むRustソースを固定。現行の `Dialogue::submit` に通した。全199件で原履歴のrole/text一致を確認した。
- 実LLMは8080の既存サービス。起動設定は `lmstudio-community/gemma-4-26B-A4B-it-QAT-MLX-4bit`、本体の要求名は `default_model`。サービスやモデルは切り替えていない。正式試験は245リクエスト。
- Normal状態を固定し、bodyを含む同じ模擬観測を全件へ供給。ゾンビ1体・スケルトン1体、石の剣1本、本人所有のhorse「シロ」1頭。各ケースは新規sessionで、Minecraftへの命令配送・実移動・音声は行わない。
- `not_request` と `other_request` は通常処理へ統合した4分類で比較。既存の5分類出力がないための対応であり、元の正解ラベルは保持する。分類器本来の5分類成績は173/199（86.9%）。
- 既存の採点は、剣の検証後handled、呼び戻しの検証後候補選択段階、敵情報の専用処理、それ以外の通常処理を観測する。詳細は保存先の `PROTOCOL.md` と `summarize.py`。

## 剣：意図の判定後に止まる

35件中、命令発行は5件。別の24件では既存LLMが `select_weapon / sword / is_request=true` を返したが、後段で不成立になった。この24件中23件のconfidenceは1.0、残る1件は0.8で、既存閾値は0.9。命令を発行した5件とこの24件を合わせた29件では、直接受付またはLLMの肯定判断までは到達している。ただしこれは出力契約やevidenceの検証を通した件数ではない。

例: movingの「剣だして」「急いで剣出して」「剣に替えてくれる？」はLLMが肯定した後に止まり、持ち替え命令がないまま「すぐ出す」「持ち替える」と返答した。`assist/intent.rs::validate_payload` が原文の明示条件・evidence・否定等を再検査するため、分類器を入口に足すだけでは同じ場所で止まる。

移動中の短い依頼だけでも既存5/12、分類器12/12。後段の自然言語条件と分類器をどのように接続するかを決め、所有・UUID・観測鮮度・実行直前検証とは分けて再評価する必要がある。

## 敵：通常会話の正答と専用処理の誤答がある

敵情報39件は全件の実返答も監査した。十分な回答16件、一部不足・余分な断定9件、誤答13件、場面が足りず一意に採点できないもの1件。これはCodexによる個別読解で、判定理由を保存している。

- 専用処理9件のうち、内容も十分だったのは3件。6件は対象・距離・要求属性などを誤った。
- 専用処理に入らない30件でも、通常会話で13件は十分に回答した。専用処理に入らないだけで失敗とは言えない。
- 「敵いない？」にはゾンビ1体・スケルトン1体と正しく返した。一方、「近くに敵いる？」にはゾンビ2体にスケルトンを足してしまう例があった。
- スケルトンの話の後の「あいつどこ？」でゾンビの距離12を回答。「一番遠い敵」に最近傍を回答。「方角は不要、数を教えて」に方向だけを回答した。

コードを確認すると、敵の種類検出はかなへ正規化した部分一致で、「どこにいるかな」の「いるか」が「イルカ」に一致し得る。今回のregression 006/007/026の位置不明回答はこの選択規則と整合する。敵情報という分類が正しくても、後段の対象・属性解釈は別の問題として残る。

## 呼び戻し：依頼認識と個体選択を分ける

呼び戻しの依頼として候補選択段階に進んだのは27/36件。movingでは12/12件だったが、これはロバ等の正しい個体を選んだ件数ではない。

固定候補には本人所有のhorse「シロ」しかいない。それでも「ロバ呼んで」「うちのロバ呼んで」でその馬への命令が発行された。名前が「剣にして」の馬を指定する入力や、履歴のハッピーガストを指す入力でもシロを選んだ。longの犬・猫を指す2件（gold=other_request）にも馬の命令が発行された。

発行された馬命令20件を監査すると、依頼に適合する候補9件、明確な対象違い8件、毛色や過去の個体との対応を確認できないもの3件だった。別の不在時確認・案内9件には、コードが低confidence等で止めた5件も含まれ、すべてをモデルの選択成功とは数えない。

候補不在時の振る舞いを含む個別監査は `recall-target-audit.json` に保存。分類器のrecall_mount正解36/36は、この個体選択の成功を示すものではない。Minecraftの候補UUIDや本人所有というコード条件が通っていても、ユーザーが求めた個体との一致は別に確認する必要がある。

## 限界と保存先

- 199件は合成193件・記録由来の発話5件・ユーザー例1件からなる分類評価用データ。通常・戦闘・panic等の状態分布や実ユーザー発話の頻度を代表しない。固定候補にない種・名の入力もあり、今回の数値を一般的な実行成功率へ外挿しない。
- 履歴には別の場面があるが、現在観測は全件同じ。現在の全敵の距離がLLMへ列挙されるわけでもない。模擬のplayer/bodyの距離関係にも不整合があるため、実機の距離精度は未評価。
- 通常会話の空応答によるgeneration_errorが1件（test-035）。HTTP通信エラー・65秒timeoutは0。1件を通常処理の正答として数えていない。
- body観測の取り込みが不十分だった初期の予備実行は別保存し、主表へ混ぜていない。
- 分類器接続後の操作・回答品質、実機移動、音声、継続会話、複数回の変動は未評価。

正本内の保存先: `.dogido_tools/experiments/2026-10-15-request-classifier-baseline/`。原文・履歴・元分類器予測、全245リクエスト/応答、全snapshot・命令、採点器、内容監査、ソースarchiveとSHA256を保持する。個別の全不一致は `scored.json` を参照。
