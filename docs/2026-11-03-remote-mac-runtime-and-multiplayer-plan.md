# クライアントPC実行・同一LAN内モデル共有・マルチプレイ対応計画

**2026-11-03の決定（計画段階・未実装）**。遊ぶMacがBonjourで共有モデルのMacを自動発見し、ドギド専用のHTTPS窓口へ接続する。初回だけ両端末でペアリングする。次回からは、共有側が起動していれば、遊ぶMacで「ドギドを起動」を開くだけでつながる。

[旧接続計画](family-single-player.md)は終了した。専用SSHサーバー・固定ポート転送・鍵入り更新ZIPの配布は廃止案として記録する。新方式の検証は§15に従う。

**対象:** ドギドのクライアント機能を複数PCで実行し、同一LAN内のLANサーバーPCから生成LLM、監視、本棚閲覧、研究データ保管を提供する。MinecraftサーバーもLANサーバーPCで運用できる構成とする。LANサーバーPC自身も、従来どおりクライアント機能を利用できる。

この文書には、利用者の関係、実アカウント名、端末所有者、外部ストレージの実パスを記録しない。個別の呼び名、接続先、保存先はGit対象外のローカル設定だけで管理する。

## 0. 旧接続方式で確認した範囲（2026-11-03）

以下はコミット `c33d73a` 時点の実装・試験記録である。後継方式での動作確認は別に行う。

- LAN中継は `default_model` だけを使い、通常JSON、usage付きSSE、最大2枚の192px PNG、`inspect_verse` / `stage_player_edit` の現行toolを再構成して通す。SSEの正常終端を一度だけ必須にし、生成の同時実行・待ち件数・HTTP処理数を有界にする。
- 任意model、adapter、URL、file参照、未知tool、追加field、内部表現採取指定は入口で拒否する。
- 既存の一括起動へ、会話画像有効・川柳内部表現無効・Dogido関連Minecraftログの限定転送を接続した。
- 呼び名は専用コマンドからkit内 `.env` の `DOGIDO_DEFAULT_CALL_NAME` 一項目だけを変更する。
- LANサーバーPCのJSONLは現在の起動logを除き、クライアントPCの限定 `.log` はserver・voice・Minecraft間で共有する書込み中lockを除き、24時間で整理する。
- 接続更新は固定manifestと全fileのSHA-256を適用前に照合し、部分展開・転送欠損ではkitや接続鍵へ書き込まない。
- 模擬HTTP・一時ファイル・起動順・停止所有権を含むLAN共有専用試験は73件成功。opt-inの実SSH・実モデルを含む5件は未実施として分離した。実Wi-Fi・実Minecraft・実音声もPhase 5の実機確認に残る。

未実装なのは、閲覧専用本棚snapshot、ModernBERTレビュー待ち収集、研究画像転送、ACK後の画像早期整理である。本棚・旅・研究保存の正本をSSDへ移した別変更とは競合させず、この段階では保存領域のコードを変更していない。

## 1. 目的

- クライアントPCでは、コマンド入力なしのダブルクリック一回でドギドを開始する。
- クライアント機能はクライアントPC専用にせず、LANサーバーPCでも同時に利用できるようにする。
- マイク、Whisper、VOICEVOX、Minecraft連携、短期状態は、実際に遊ぶクライアントPCで動かす。
- 重い生成LLMだけを同一LAN内のLANサーバーPCから借りる。
- LANサーバーPCで、クライアントPCのドギド関連ログを確認できるようにする。
- 記憶と本棚は実行環境ごとに分離し、LANサーバーPCでは閲覧専用にする。
- Minecraftのリモートマルチプレイでも、クライアント側で可能な会話・観測・HUDを維持する。
- ModernBERT改善用の文字データと、画像分析用の実画像を、外部公開せず収集する。
- 容量に制約のあるクライアントPCへ、画像・ログ・研究成果を蓄積し続けない。

## 2. 対象外

- インターネットへのドギドAPI、LLM API、本棚、ログ画面の公開。
- OSの通常リモートログイン、ファイル共有、管理者アカウントの変更。
- 任意モデル、任意URL、任意toolを使える汎用LLM中継。
- クライアントPCでの川柳内部表現 `hidden.f32` 採取。
- Minecraftアカウント、ワールド、インベントリ、プレイヤーデータの移行・統合。
- リモートMinecraftサーバー上での、権限のないentity移動や汎用コマンド実行。
- 収集データのGitHub、外部クラウド、公開教材への自動送信。

## 3. 構成

```text
クライアントPC
  Minecraft Java + Fabric client mod
           │ 127.0.0.1
           ▼
  Rustドギド本体
  ├─ 専用memory_dir
  ├─ Whisper / VAD / AEC / マイク
  ├─ VOICEVOX / 音声再生
  ├─ 容量上限付きログ・転送待ち領域
  └─ LANサーバーPCへの接続
              │ 遊ぶMacからHTTPS要求（接続先はBonjourで発見）
              ▼
LANサーバーPC
  限定LLM窓口 ── llama-server / default_model
  ├─ クライアントPCログの表示・24時間保持
  ├─ 本棚の閲覧専用コピー
  ├─ ModernBERTレビュー待ちデータ
  └─ 画像分析用の外部ストレージ

LANサーバーPC上のMinecraftサーバーは、上のドギド接続と独立して動かす。
```

各PCで使うクライアント機能は、Minecraft、Rust本体、マイク入力、VOICEVOX、音声再生、専用memoryを同じPCに置く。LANサーバー機能は既存のクライアント機能を置き換えず、LANサーバーPCでもローカルのクライアント機能を並行して起動できる。クライアントPCのFabric modとRust本体も従来どおりloopbackだけで接続する。

共有モデルのMac自身はloopbackでLLMを利用する。別のMacで遊ぶときは、生成依頼、ログ、本棚のコピー、研究データの転送をすべて遊ぶMacから開始する。生成結果（SSEを含む）と保存確認は、それぞれのHTTPS要求への応答として返す。共有モデルのMacから遊ぶMacへの新規接続や、遊ぶMacのLAN待受は不要。各Macのsession、memory、音声、ログは分ける。

## 4. 旧接続方式の実装記録

旧配布セットは以下の構成だった。後継方式でも必要な機能は、§1の目的と§13のセキュリティ要件に基づいて選ぶ。

- クライアントPCの一括起動：専用接続、VOICEVOX、Rust本体、音声入力を一つの可視ランチャーから順番に開始する。
- LANサーバーPCの限定接続：鍵認証、固定port forward、shell・SFTP・任意転送の拒否。
- LLM窓口：固定のloopbackモデルだけへ接続し、モデル切替や任意endpointを拒否する。
- ログ転送：クライアントPC側へも保存しつつ、会話処理を待たせずLANサーバーPCへ転送する。
- 専用memory：クライアントPCの記憶とワールドを他環境から分離する。

実装着手時の中継は旧契約の文字列・非stream要求を前提としていた。現行のGemma 4構成に合わせ、次を厳密な許可リストとして追加した。

- SSEによる文単位stream応答。
- 川柳相談で実際に使う既存native toolとtool結果。
- `data:image/png;base64,...` の画像part。任意URLと任意ファイル参照は禁止する。
- `default_model` と、既存のtoken・temperature・thinking無効設定。
- 通常会話、環境反応、川柳で共有する現在の一回生成契約。

人格、会話方針、観測方針のプロンプト本文は、このクライアントPC対応だけを理由に変更しない。視覚入力仕様の実装で文面変更が必要な場合は、別作業として「元プロンプト → 新プロンプト」を提示し、承認後に反映・試験する。

## 5. 起動と停止

### 初回だけ：2台のMacを登録する

1. 共有モデルのMacで「このLANでドギドを受け付ける」を選ぶ。共有側は同一LANにドギドの窓口をBonjourで知らせ、新しい端末の登録を一時的に受け付ける。
2. 遊ぶMacで「ドギドを起動」を開き、見つかった共有Macを選ぶ。IPアドレスの入力や接続ファイルの受け渡しは不要。
3. 両画面に表示される、その回の接続相手に結び付いた確認番号を見比べる。一致を確認して両側で承認すると、各Macが相手を登録する。不一致・取消・期限切れなら登録せず、会話や本棚のデータも送らない。

### 毎回：共有モデルのMacで受付を開く

一つのダブルクリック起動で、次を確認・開始する。

1. 共有 `llama-server` の `default_model` が応答することを確認する。
2. ドギド専用のHTTPS窓口を開始し、Bonjourで知らせる。登録済みの端末はそのまま利用でき、新しい端末の追加は初回登録の操作から行う。
3. 接続先、ログ保存先、画像保存先の利用可否を表示する。
4. Minecraftサーバーや既存LLMを勝手に開始・停止・切替しない。

### 毎回：遊ぶMacで「ドギドを起動」を開く

一つのダブルクリック起動で、次を順番に行う。

1. 二重起動を拒否する。
2. Bonjourで現在の接続先を探し、ペアリング済みの共有Macであることを照合してHTTPSで接続する。共有側も登録済みの端末であることを確認してから、モデル応答の確認へ進む。IPアドレスが変わっても、同じ相手なら再登録は不要。
3. VOICEVOXを確認し、未起動ならアプリを開く。
4. Rust本体を開始し、`runtime=rust`、`dialogue_ready=true` を待つ。
5. Rust音声入力を開始する。
6. 準備完了と、終了方法を日本語で表示する。
7. 終了時は、自身が起動した音声、本体、Minecraft限定ログ、専用接続だけを逆順に停止する。

共有側を発見できない間は「共有Macを待っています」と表示する。起動前・スリープ中・通信断のいずれでも、遊ぶMacから間隔を空けて探し直し、同じ相手が復帰したら自動で接続を再開する。待機は利用者が終了できる。同名の別端末や登録解除など相手を確認できない場合はデータを送らず、再登録が必要と表示する。モデルが未起動の場合は接続先の探索と区別して表示する。

## 6. プレイヤーの呼び名

ドギドが口にする呼び名には、既存設定を使う。

```dotenv
DOGIDO_DEFAULT_CALL_NAME=<呼んでほしい名前>
```

- 呼び名は通常会話、危険時の警告、環境反応、川柳材料へ渡す。
- Minecraftの実アカウント名、UUID、所有者確認、接続認証は変更しない。
- 設定が空なら既存のfallbackを使う。
- 前後の空白と制御文字を除き、実装時に短い上限を設ける。
- 名前専用の音声素材がなくても、VOICEVOXによる全文読み上げへ戻る。
- 実アカウント名や実際の呼び名は、配布物、文書、Git管理ファイルへ書かない。

Minecraft mod側の `player_name_override` は、観測や旅の記録上の名前まで置換するため、この用途には使わない。

## 7. Minecraftマルチプレイ

Fabric adapterはクライアントmodとして動作する。リモートMinecraftサーバーへ接続している間も、クライアントで取得できる観測、会話、HUD、クライアント内hotbar選択はクライアントPCのRust本体へ送れる。

同じMinecraftサーバーへ同時参加する各クライアントは、Minecraftサーバー上で別の認証済みプレイヤーidentityを持つことを前提とする。同一identityの同時利用や、`online-mode=false` による回避は設計対象にしない。

シングルプレイのintegrated server権限を使う機能は、リモートマルチプレイで同じようには実行できない。特に `integrated_server.horse.recall.v2` の乗れる動物の呼び戻しは、リモートサーバーでは利用不可とする。必要になった場合は、許可済みserver-side modと実行前再検証を別仕様で設計する。

LANサーバーPCでMinecraftサーバーと生成LLMを同時運用するため、LANサーバーPC側クライアント・クライアントPCクライアントから生成要求が重なった場合の待ち時間を実測する。測定前にモデル並列度を変更しない。

## 8. 記憶と本棚

- クライアントPCは専用 `memory_dir` を正本として使う。
- Minecraftアカウント名を本棚のテナントキーにしない。
- LANサーバーPCには閲覧専用コピーを置き、編集・削除・採否・読み訂正を受け付けない。
- 句、推敲、旅の記録、メモ、本棚用写真はhash付きsnapshotとして転送する。
- 転送失敗中もクライアントPCの正本へ保存を続ける。
- LANサーバーPCの閲覧用コピーと将来の外部ストレージとの間で、双方向mergeを行わない。
- 外部ストレージ移行は、コピー、hash照合、参照先切替の順で明示的に行う。起動時に自動移動しない。

LANサーバーPCの閲覧用コピーは正本ではない。SSD正本を使う既存環境とはarchive IDと保存領域を分離する。クライアントPC側の記憶までLANサーバーPCのSSD正本にする場合は、単なるsnapshot転送ではなく書込み所有権・通信断・CAS・ACKを持つ別仕様が必要なため、この計画の最小実装には含めない。

本棚に結び付いた原寸写真は、画像分析用フォルダへ混ぜない。LANサーバーPCまたは将来の本棚用外部ストレージで別管理する。容量に制約のあるクライアントPCには、転送・照合後に本棚表示用の小さなサムネイルだけを残す構成を目標とする。

## 9. ログ

### 対象

- Rust本体の標準出力・エラー。
- 音声入力、Whisper、AECの状態と失敗理由。
- LLM要求の開始・終了・所要時間・usage。本文や認証値はLLM窓口のHTTPログへ出さない。
- Minecraft/Fabricのうち、Dogidoが付けた行と関連エラーだけ。Minecraftの全 `latest.log` は転送しない。

### 保持

- クライアントPCのDogido専用ログと、LANサーバーPCへ転送されたクライアントPCログは直近24時間だけ保持する。
- 起動時と、稼働中の1日1回に、管理対象ディレクトリ内の期限切れファイルだけを削除する。
- 書き込み中のログ、別アプリのログ、Minecraft本体のログは削除しない。
- ModernBERT収集データ、画像分析データ、本棚、旅の記録はログ削除の対象にしない。
- 通信断中はクライアントPCの有界キューへ残し、会話処理を待たせない。上限超過時は省略件数を記録する。

## 10. 低容量モード

クライアントPCでは次を既定とする。

- ModernBERT採用モデル2本は、推論に必要な固定容量として保持する。
- `DOGIDO_HAIKU_INTERNAL_CAPTURE_ENABLED=false` を維持する。
- 会話画像のbase64を履歴、episode、長期記憶へ保存しない。
- 通常の会話画像は既存どおり一時保存し、未転送時も最終利用ACKから24時間後にhash確認して整理する。
- 研究用画像をLANサーバーPCがhash確認して保存した後は、クライアントPCの一時PNGを24時間より前に整理できる。
- 転送待ち領域には固定の容量上限を設ける。上限到達時は、Minecraft、本棚、通常会話を止めず、研究用の新規採取だけを停止して通知する。
- 一般のMinecraftスクリーンショットは削除・移動・圧縮しない。

## 11. ModernBERT改善用データ

分類器の予測を自動的に正解へ昇格させない。実行時はレビュー待ち候補として、固定schemaの小さなJSONLをLANサーバーPCへ送る。

保存候補は次に限定する。

- 入力原文、正規化後、意味解釈後を混同しない別フィールド。
- 入力元がvoiceかtypedか。
- normalまたはsenryuの受付モード。
- 使用モデルと採用記録のhash。
- 予測ラベル、全ラベル確率、token数、推論時間。
- 入力世代、取消、遅延、選択された実行経路。
- 学習に必要な場合だけの有界な直近発話。世界の全snapshotは保存しない。
- 人が後から付ける正解ラベル、採用・保留・除外の状態。

録音音声は保存しない。LANサーバーPCのレビュー画面で人が採用し、正解ラベルを指定した行だけを、既存の教材CSVへ書き出せるようにする。未レビュー、取消、別モードへ遅延到着した結果は、その状態を残したまま正解データへ入れない。

## 12. 画像分析用データ

画像分析用の保存先は、Git対象外のローカル設定で指定した外部ストレージ上の専用フォルダとする。文書には実パスや実アカウント名を書かない。

### 専用フォルダの契約

- フォルダ直下には完成済みの `.png` 画像だけを置く。
- JSON、ログ、台帳、本文、音声、一時ファイルを置かない。
- 一時ファイルは同一外部ストレージ上の別stagingへ書き、hash確認後に完成PNGだけを原子的に移す。
- 外部ボリュームが実際にmountされ、期待するvolume identityと一致するときだけ書く。
- ボリューム未接続・権限不足・空き容量不足では、内蔵SSDの同名パスを作らず採取を保留する。
- 同一画像はSHA-256で重複保存しない。

画像名には、個人名を含まない採取時刻、pair ID、役割、hash短縮値を使う。

```text
<UTC時刻>_<pair-id>_before_<sha12>.png
<UTC時刻>_<pair-id>_after_<sha12>.png
<UTC時刻>_<pair-id>_before-192_<sha12>.png
<UTC時刻>_<pair-id>_after-192_<sha12>.png
```

保存対象は、Gemmaへ実際に提示した画像と、その比較元に限定する。動画、無関係な連続frame、録音音声は保存しない。原寸画像と実際のモデル入力192px画像は別hashとして保存し、後から同じ前処理を推定しなくてよい形にする。

比較状態、撮影時の身体方位、PLAYER枠、撮影間隔、モデル使用有無、モデルの発話・沈黙結果、処理時間、完全hashは、小容量の管理台帳へ保存する。管理台帳は画像専用フォルダへ入れず、LANサーバーPCのアプリ管理領域に置き、画像の完全hashで参照する。

LANサーバーPC側で完成PNGのhashを再計算し、原子的保存が完了したACKを返した後だけ、クライアントPCの研究用一時PNGを早期整理する。外部ストレージを自動公開・同期しない。

## 13. セキュリティとプライバシー

- Rust本体、VOICEVOX、Fabric接続は各PCのloopbackに限定する。
- Bonjourの名前・IPは発見だけに使う。初回承認で端末の認証情報を登録し、以後はHTTPS接続ごとに双方が登録した相手を照合する。登録は共有側から端末単位で解除できる。モデル本体はloopbackに置き、LANから利用できるのは用途を限定したドギド窓口だけとする。
- shell、SFTP、TTY、agent forwarding、任意port forward、リモートコマンドを拒否する。
- LLM窓口は固定モデル、固定endpoint、既知のmessage/tool/image外形だけを再構成して転送する。
- routerのport forwardingやUPnPによる外部公開を行わない。
- 秘密鍵、認証token、実アカウント名、個別の保存先を配布manifest・ログ・文書へ書かない。
- 収集物には発話、Minecraft画面、座標、会話、旅の内容が含まれ得る。外部提供は、人が選択・匿名化した別の明示操作に限定する。

## 14. 実装順

最初にBonjourでの発見、初回ペアリング、HTTPSでの自動再接続を実装し、遊ぶMacを受信待ちにせず往復できることを確認する。その後に限定中継・一括起動・本棚転送をつなぐ。§0の試験件数は旧方式の記録として扱う。

### Phase 1：現行本体へ追従した限定中継

- stream、既知tool、PNG image partを許可する。
- 任意モデル、任意URL、任意tool、任意ファイル参照を拒否する試験を維持する。
- 旧モデル名や旧案内を `default_model` と現行Gemma運用へ更新する。

### Phase 2：一括起動と呼び名

- クライアントPCとLANサーバーPCの一括起動を現行Rustで再確認する。
- `DOGIDO_DEFAULT_CALL_NAME` をクライアントPCのローカル設定へ追加する。
- 呼び名とMinecraft identityを分離したまま、通常会話・警告・川柳へ反映する。

### Phase 3：ログと本棚

- Dogido関連Minecraftログの限定転送を追加する。
- 両PCのDogidoログを24時間で整理する。
- 本棚snapshotをLANサーバーPCへ送り、閲覧専用で表示する。

### Phase 4：研究データ

- ModernBERTの未レビュー収集schemaとレビュー画面を追加する。
- 画像・管理台帳を分離し、外部ストレージへhash付きで保存する。
- ACK後のクライアントPC早期整理と、未接続時の採取保留を追加する。

### Phase 5：実機確認

- クライアントPCのマイク、実Whisper、実VOICEVOX、Minecraft、画像、保存、通信断を確認する。
- LANサーバーPCのMinecraftサーバーとLLMを同時に動かし、複数クライアント要求時の待ち時間を測る。
- 必要な確認が済んだら完了報告し、別機能の実装へ広げない。

## 15. 検証計画

各試験のコードまたはケース定義の近くへ、下表と同じ見込み・合格条件・確認範囲を200字以内で記載する。

| 項目 | 見込み | 合格条件 | 確認範囲 |
|---|---|---|---|
| 初回登録 | 両画面で今回の相手を確認すれば、IP入力なしで登録できる | 両側の承認後だけ利用でき、不一致・期限切れでは登録もデータ送信も起きない | 模擬端末での拒否試験＋同一LANの2台で画面確認 |
| 次回の起動と復帰 | 発見と端末照合を分ければ、アドレスが変わっても同じMacへ戻れる | 遊ぶMacで「ドギドを起動」だけで接続し、IP変更・スリープ復帰後も再承認なしで同じ端末へ接続する。同名の別端末や登録解除済みの端末は拒否する | 模擬識別試験＋実Wi-Fiでの再起動・復帰 |
| 接続の向き | 遊ぶMacからの要求に応答すれば、逆向きの新規接続は不要 | 遊ぶMacへの新規着信を遮った状態でも、生成応答を受信し、本棚転送の保存確認が返る | 模擬HTTPS＋2台のMacでの通信方向確認 |
| 中継の許可範囲 | 現行Dogidoの既知要求だけを再構成すれば、機能を保ったまま中継を汎用APIにしない | text、stream、既知tool、PNGが通り、任意model・URL・tool・file URL・追加fieldは拒否される | 模擬HTTP。実モデル品質は別確認 |
| 一括起動 | readinessを順に待てば、音声が本体準備前に開始せず、一回の終了で所有processだけ止まる | 接続→VOICEVOX→Rust ready→音声の順になり、既存のMinecraft・LLM・VOICEVOXを停止しない | 自動process模擬＋クライアントPC実機 |
| 呼び名 | 既存の動的呼び名設定を使えば、Minecraft identityを変えずに発話だけ変更できる | 通常会話材料、固定警告、川柳材料が設定名になり、登録UUID・所有者判定は不変 | 自動投影試験。実際の自然な呼び方は実モデル確認 |
| ログ保持 | 管理対象を固定し24時間で整理すれば、障害確認に必要な直近分だけ残る | 期限切れの閉じたDogidoログだけ削除し、当日・書込中・Minecraft・研究・本棚は残る | 一時ディレクトリ試験＋日跨ぎ実機 |
| 本棚分離 | 専用memoryを正本、遠隔側をread-onlyにすれば、別環境の記憶と編集が混ざらない | クライアントPCの句・旅・写真が閲覧コピーに現れ、遠隔側の更新要求は拒否され、正本hashが不変 | 模擬保存＋両PC実機。長期HDD運用は別確認 |
| ModernBERT収集 | 予測と人の正解を分ければ、未確認予測を誤って教師データにしない | 原文・mode・予測・確率・結果を保存し、review済み行だけCSVへ出る | 固定分類結果による接続試験。再学習品質は対象外 |
| 画像保存 | 外部volumeとhashを確認してからACKすれば、画像を内蔵SSDへ誤保存せず早期整理できる | 画像専用先には完成PNGだけがあり、重複hashは1個、未mount・権限不足時は保存もACKも行わない | 模擬filesystem＋利用者による外部ストレージ確認 |
| 画像対応 | 実際にGemmaへ見せたframeだけを保存すれば、モデル結果と入力を後から対応付けられる | before/afterと192px版のhashが台帳と一致し、未使用frameやbase64を長期記憶へ残さない | 模擬モデル要求＋保存画像レビュー。認識精度は別評価 |
| 通信断 | ログ・研究転送を会話workerから分離すれば、LAN断でゲーム処理を待たせない | 会話処理が継続し、有界キューだけ増え、復旧後に再送する。上限では研究採取を止めて件数を通知する | 模擬切断＋同一Wi-Fi実機 |
| マルチプレイ | client modの観測とローカルRustを使えば、リモートサーバーでも会話・HUDを維持できる | 別identityの2クライアントが参加し、各Dogidoのsession・memory・音声が交差しない。horse recallは利用可能と誤表示しない | 実Minecraftサーバー。シングルプレイ試験から推定しない |
| 同時負荷 | LANサーバーPCでMinecraftサーバーとLLMが共存しても、実測から許容範囲を判断できる | 代表的な同時発話で生成時間、timeout、Minecraft tick、音切れを記録し、失敗を隠さない | 実LLM・実Minecraft・実音声。模擬成功とは分ける |

## 16. 完了条件

- 初回だけ両画面でペアリングし、次回からは遊ぶMacで「ドギドを起動」を開くだけでつながる。共有側のIP変更やスリープからも、遊ぶMacへの新規着信なしに復帰する。
- クライアントPCで、コマンド入力なしの一括起動から実Minecraft・実音声の一巡が成功する。
- 現行の通常会話、画像、環境反応、川柳相談が限定中継を通る。
- LANサーバーPCで直近ログと閲覧専用本棚を確認できる。
- ログが24時間を超えて蓄積しない。
- ModernBERT候補と画像分析データが、外部公開なしで指定先へ保存される。
- 外部画像保存先には画像だけが入り、実パスとアカウント名が文書・Git・ログへ出ない。
- クライアントPCの内部表現採取が無効である。
- リモートマルチプレイの対応機能と利用不可機能を実機結果に基づいて区別できる。
- 自動試験、模擬通信、実モデル、実Minecraft、実マイク、実再生、外部ストレージ確認を別々に報告する。
