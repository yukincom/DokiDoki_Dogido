## 2. 課題パターンの詳細分析

### 2.1 コメントの意味が曖昧・文脈依存が強すぎる例

#### 例1: `dogido-rust/src/address.rs` L1
```rust
//! 国語対話からの話題移管。宛先不明の入力は一件だけ、元の期限・IDで保持する。
```
- **問題点**: 「話題移管」が何を指すのか（誰から誰へ移管するのか）、どういう状況で「宛先不明」が発生し、その1件が誰によっていつ破棄・消費されるのかがこのファイル内だけでは読み取れない。
- **改善案**:
  ```rust
  //! プレイヤーの発話がドギド（相棒）宛てか国語対話（辞書検索）宛てか判別できない場合の入力バッファ管理。
  //! 宛先判定が保留された入力は最新の1件のみを元の有効期限・発話IDのまま保持し、
  //! 次の入力や確認ターンで宛先が確定した際に再ルーティングする。古い保留入力は上書き破棄される。
  ```

#### 例2: `dogido-rust/src/dialogue/mod.rs` L433
```rust
// submitと同じlock順序。shutdownが取りこぼす未登録jobを作らない。
```
- **問題点**: 「どのロックとどのロックの順序か」が具体名で書かれておらず、デッドロック回避の文脈が他のAIに伝わりにくい。
- **改善案**:
  ```rust
  // デッドロックを防ぐため、job投入時（submit）と同一の順序（dataロック → serialロック）で取得する。
  // また、シャットダウン処理中に新規jobが登録されてリークしないよう、ロック保持下で残存jobを回収する。
  ```

### 2.2 実態との乖離・ミスリーディングを招く例

#### 例1: `dogido-rust/src/events/semantic.rs` L1
```rust
//! models.pyの3つのafter-validator。構造化された観測の意味だけを検査する。
```
- **問題点**: `models.py` はすでにリポジトリ上で稼働していない（または撤去予定の旧Pythonコード）。新しい開発者やAIが「`models.py` を見に行かなければいけないのか？」と混乱する。
- **改善案**:
  ```rust
  //! Fabricから受信した構造化イベントのセマンティック（意味論）検証。
  //! フィールドの型検査（wire層）を通過した観測データに対し、
  //! 「座標の妥当性」「エンティティ状態の整合性」などゲーム世界の前提条件を満たしているかを検査する。
  ```

#### 例2: `dogido-rust/src/threats/groups.rs` L123
```rust
// Python datetime.isoformatと同じ6桁の小数・UTC offsetで既存の文面を選ぶ。
```
- **問題点**: 実装は `chrono::DateTime<Utc>` を使ったフォーマット処理だが、「なぜPythonと同じにする必要があるのか」の理由（プロンプト側や外部テンプレート、あるいは回帰テストfixtureとの互換性）が省かれているため、単なるPythonへの未練に見えてしまう。
- **改善案**:
  ```rust
  // 発話文面テンプレートおよび回帰テストfixtureとの完全一致を保つため、
  // タイムスタンプはマイクロ秒6桁＋UTCオフセット（例: 2026-10-04T10:00:00.000000+00:00）で整形する。
  ```

### 2.3 ネガティブ制約（〜しない）過多による認知負荷の例

コードベース全体に見られる特徴として、**AGENTS.mdの設計原則を遵守するために書かれた「否定形コメント」** が多い。

```rust
// 視認消失・死亡音・経験値は撃破の根拠にしない。
// 全視認を含む観測とその受信時刻。部分通知で消去・延命しない。
// 記憶の読込み・更新や世界の位置推定はしない。
// 候補検索結果は存在の証拠にしない。
```

- **分析**: これらは「AIが勝手に推測コードを書かないためのガード」として非常に価値が高い（AGENTS.mdの精神を強く反映している）。
- **課題**: しかし、「〜しない」だけが連続すると、**「では、何をもって条件成立とするのか？」** がコードの奥底まで読まないと分からない。
- **改善アプローチ**: **「目的（Positive）＋ Guard（Negative）」の2部構成**にする。
  - 例: `// 撃破判定はFabricからの論理サーバー死亡イベントおよび実爆発パケットのみを根拠とする（視認消失・死亡音・経験値ドロップ等では誤認防止のため撃破扱いにしない）。`

## 3. 「人間とAIが最も働きやすい」コメント設計指針

DokiDoki-Dogido は「Rust状態機械・優先規則が主、LLMが従」という極めて厳密なアーキテクチャを持つ。
今後の開発において、Claude、Grok、GeminiなどのAIエージェントや人間の開発者が迷わず作業できるようにするための標準コメント構成を以下に定義する。

### 3.1 モジュールトップ (`//!`) の標準テンプレート
各モジュールの先頭には以下の4要素を明記する：
```rust
//! # モジュール名（例: 川柳生成エンジン）
//! 
//! ## 責務 (Role)
//! このモジュールが担当する単一の責務（例: 観測データから5/7/5の句候補を生成・検証する）。
//!
//! ## 所有権と境界 (Boundary)
//! - **所有するもの**: 句の候補生成ループ、音数・重複の検証。
//! - **所有しないもの**: 句の永続化（dialogue/memoryが担当）、音声合成（audioが担当）。
//!
//! ## 不変条件・安全規則 (Invariants)
//! - LLMの生成結果は必ずRust側で音数・禁止語チェックを行い、無検証で採用しない。
//! - 失敗時は必ずカタログフォールバックを返す。
```

### 3.2 主要関数・構造体 (`///`) の標準テンプレート
```rust
/// 関数の目的（1行で要約）。
///
/// ### 引数 / 前提条件
/// - `complete`: 全体観測か部分通知か。部分通知の場合は既存の敵キャッシュをクリアしてはならない。
///
/// ### 戻り値 / 副作用
/// - 新たに発話すべき警告がある場合は `Some(Decision)`、抑制すべき場合は `None`。
/// - ※ この関数呼び出し自体は音声I/Oを行わない（呼び出し側が配送をキューイングする）。
```

### 3.3 インラインコメント (`//`) の使い分け
- **Why（なぜこのコードなのか）を書く**: コードを見れば分かる「何をしているか」ではなく、「なぜ他の書き方（標準関数等）ではダメなのか」「なぜこの順序でロックを取るのか」を書く。
- **「〜しない」には理由を添える**: 「○○はしない」の後ろに「〜の誤認・二重実行を防ぐため」を必ずセットにする。

## 4. モジュール別：推奨コメント追加・改善箇所一覧

### 4.1 `dogido-rust/src/dialogue/`（対話・セッション管理）
- **現状**: コメントは比較的多いが、ロック順序（`data` mutex と `serial` mutex）および `epoch`（世代）によるキャンセル・反映破棄のライフサイクルが各関数に分散している。
- **改善推奨**:
  - `dialogue/mod.rs`: `Session` 構造体のフィールドごとに、「どのロックで保護されているか」「どのworkerが更新権限を持つか」を明記。
  - `dialogue/chat_runtime.rs`: プレイヤー入力が届いてから、planner呼び出し → カタログ照合 → 発話文生成 → 音声合成待ち に至るパイプラインのフェーズ遷移を関数の上部にフロー図コメントとして記載。

### 4.2 `dogido-rust/src/haiku/`（川柳生成・検査）
- **現状**: 生成処理（`generation.rs`）にはコメントがついたが、材料準備（`preparation.rs`, `materials/`）が無防備。
- **改善推奨**:
  - `haiku/preparation.rs`: 観測されたブロック・モブ・天候・プレイヤーの感情タグが、どのように `HaikuMaterial` にマッピングされるかのルールを明記。
  - `haiku/meter.rs`: ひらがな変換後のモーラ数（音数）計算において、拗音（ゃゅょ）や促音（っ）、長音（ー）をどうカウントするかの境界条件を明記。

### 4.3 `dogido-rust/src/combat/`（戦闘判断エンジン）
- **現状**: ネガティブ制約コメント（消さない、捏造しない）が最も洗練されている。
- **改善推奨**:
  - 「消さない」理由の背後にある「Minecraft Fabricからのパケット送信仕様（部分パケットで視認リストが空で届くことがある）」という背景事情を `combat/core.rs` のトップに注記する。これがないと、将来のAIが「空配列が来たら敵がいなくなったと判定するリファクタ」を行ってしまう危険がある。

### 4.4 `dogido-rust/src/events/`（Fabric通信・イベントスキーマ）
- **現状**: 2,000行近くあるが、最もコメントが不足している。
- **改善推奨**:
  - `events/models.rs`: 各 `struct`（例: `PlayerStatusEvent`, `MobSpawnEvent` など）に対し、どのFabricイベントハンドラから送られてくるかと、必須項目の単位（座標: double、tick: u64、ヘルス: float）を明記。

### 4.5 `dogido-rust/src/voice/`（音声認識・入出力）
- **現状**: `mod.rs` 以外は英語ドキュメントまたはコメントなし。
- **改善推奨**:
  - `voice/stt.rs`: whisper.cpp の推論実行、無音スキップ判定、VAD（Voice Activity Detection）との連携タイムアウトを記述。
  - `voice/process.rs`: 子プロセス管理（macOSでのプロセスグループ設定、SIGTERM/SIGKILLの猶予時間）の意図を明記。

## 5. まとめと次のアクション

今回の点検により、現在のコードベースは**「アーキテクチャ境界の破綻を防ぐためのガードコメント」が極めて高品質に配置され始めている**一方で、**「コード全体の基本理解を促すドキュメンテーション」「未コメントの大規模モジュール」が課題**であることが明らかになりました。

### 推奨される作業ステップ
1. **フェーズ1（誤解の排除）**: `models.py` 等の旧Pythonコード言及コメントを、現在のRustネイティブ仕様に基づいた文面に更新する。
2. **フェーズ2（重要基盤の補強）**: コメント皆無の上位ファイル（`events/models.rs`, `haiku/preparation.rs`, `voice/stt.rs`）に、モジュール概要と主要構造体のドキュメント（`///`）を追加する。
3. **フェーズ3（否定コメントの補完）**: 「〜しない」コメントに対し、「なぜなら〜の誤作動を防ぐため。正しくは〜で判定する」というポジティブな理由・代替手段を併記する。
